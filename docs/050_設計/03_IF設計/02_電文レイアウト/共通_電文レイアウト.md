## 1. 概要

本文書は、API グループごとの電文レイアウト（[認証](認証_電文レイアウト.md)、[アカウント](アカウント_電文レイアウト.md)、[ユーザ管理](ユーザ管理_電文レイアウト.md)、[権限](権限_電文レイアウト.md)、[銀行口座](銀行口座_電文レイアウト.md)、[ラベル](ラベル_電文レイアウト.md)、[取引](取引_電文レイアウト.md)、[管理](管理_電文レイアウト.md)）に共通する事項をまとめる。

- 要求の URL の組み立て（`serverApiUrl`）。
- 要求ヘッダー（認証トークン、要求本文の形式）。
- バックエンドのパスごとの認証・認可の要件。
- エラー応答の共通の形式（RFC 7807 の Problem Details）。
- 成功通知のためのレスポンスヘッダー（alert、error、params）。
- ページングのレスポンスヘッダー（`X-Total-Count`、`Link`）。
- 並び替えとページングのクエリパラメーター。
- フロントエンドのインターセプターによる共通処理。

対象はフロントエンドのコミット `570a360` とバックエンドのコミット `423e462` である。文書とコードが食い違う場合はコードを正とする。バックエンドのパスには「バックエンドの」を添える（バックエンドのパスはフロントエンドのリポジトリには存在しない）。

## 2. 要求の URL

| 項目 | 内容 | 根拠 |
| --- | --- | --- |
| 基底 URL | `serverApiUrl` の直後に各 API のパス（`api/...`、`management/...`）を付けた文字列である。例: `${serverApiUrl}api/account` | `src/app/core/auth/account.service.ts`（`fetch()`）、各サービスの `resourceUrl` |
| `serverApiUrl` の値 | ビルド時定数 `SERVER_API_URL` である | `src/app/config/endpoint.constants.ts` |
| `SERVER_API_URL` の既定値 | 空文字列（`''`）。このとき URL はフロントエンドと同じオリジンへの相対パスになる | `angular.json`（`define` の `SERVER_API_URL`） |
| `SERVER_API_URL` の変更 | ビルド時に環境変数 `SERVER_API_URL` を指定する。末尾に `/` がないときはプラグインが付ける。別オリジンを指定したときはバックエンドの CORS の設定が必要である | `build-plugins/define-esbuild.ts`（`withTrailingSlash()`）、バックエンドの `src/main/resources/config/application-dev.yml`（`jhipster.cors`） |
| 開発時のプロキシー | 開発サーバーは `^/(api\|management\|v3/api-docs\|h2-console)` に一致する要求を `http://127.0.0.1:8080` へ転送する | `proxy.config.mjs` |
| パスパラメーターの符号化 | サービスはパスパラメーターを `encodeURIComponent()` で符号化する | 各サービスの `find()`、`update()`、`delete()` など |

本文書の各電文レイアウトでは、パスは `serverApiUrl` を除いた `api/...`、`management/...` の形で書き、パスパラメーターは `{id}`、`{login}`、`{name}` のように波括弧で書く。

## 3. 要求ヘッダー

| ヘッダー | 値 | 付ける条件 | 根拠 |
| --- | --- | --- | --- |
| `Authorization` | `Bearer <トークン>` | 保存された認証トークンがあるとき、`authInterceptor` がすべての HTTP 要求に付ける | `src/app/core/interceptor/auth.interceptor.ts`、`src/app/core/auth/state-storage.service.ts`（`getAuthenticationToken()`） |
| `Content-Type` | `application/json` | `HttpClient` が要求本文にオブジェクトを渡すとき（Angular の標準の動きであり、本リポジトリのコードではない） | 各サービスの `this.http.post()`、`this.http.put()`、`this.http.patch()`（Angular の `HttpClient` のメソッド。呼び出し箇所は `src/app/entities/bank-account/service/bank-account.service.ts` など） |
| `Accept` | バックエンドが `application/json` で返す（フロントエンドは `Accept` を明示的に設定していない） | なし | 各サービスの `http.get()`、`http.post<...>()` など |

`authInterceptor` がトークンを付けないのは、要求の URL が空のとき、または URL が `http` で始まり、かつ `serverApiUrl` で始まらないときだけである（`src/app/core/interceptor/auth.interceptor.ts`）。本リポジトリのサービスはすべて `serverApiUrl` で始まる URL を使うため、該当する要求はない。

トークンの保存先とキーは次のとおりである。

| 項目 | 内容 | 根拠 |
| --- | --- | --- |
| ストレージのキー | `jhi-authenticationToken` | `src/app/shared/jhipster/constants.ts`（`AUTHENTICATION_TOKEN_KEY`） |
| 「Remember me」がオンのとき | `localStorage` に保存する | `src/app/core/auth/state-storage.service.ts`（`storeAuthenticationToken()`） |
| 「Remember me」がオフのとき | `sessionStorage` に保存する | 同上 |
| 読み取り | `localStorage` を先に探し、なければ `sessionStorage` を探す。値は `JSON.parse()` で戻す | 同上（`getAuthenticationToken()`） |
| 削除 | `localStorage` と `sessionStorage` の両方から削除する | 同上（`clearAuthenticationToken()`） |

## 4. バックエンドのパスごとの認証・認可の要件

バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java` の `requestMatchers` による。上から順に適用される。

| パス | HTTP メソッド | 要件 | フロントエンドの呼び出し元 |
| --- | --- | --- | --- |
| `/api/authenticate` | POST | 認証不要 | `AuthServerProvider.login()`（[認証](認証_電文レイアウト.md)） |
| `/api/authenticate` | GET | 認証不要 | なし（フロントエンドは呼ばない） |
| `/api/register` | すべて | 認証不要 | `RegisterService.save()` |
| `/api/activate` | すべて | 認証不要 | `ActivateService.get()` |
| `/api/account/reset-password/init` | すべて | 認証不要 | `PasswordResetInitService.save()` |
| `/api/account/reset-password/finish` | すべて | 認証不要 | `PasswordResetFinishService.save()` |
| `/api/admin/**` | すべて | `ROLE_ADMIN` | `UserManagementService` |
| `/api/**` | すべて | 認証済みであること | `AccountService`、`BankAccountService`、`LabelService`、`OperationService`、`AuthorityService`、`UserService` |
| `/v3/api-docs/**` | すべて | `ROLE_ADMIN` | なし（Swagger UI のページが読み込む。API 画面の設計書を参照） |
| `/management/health`、`/management/health/**` | すべて | 認証不要 | `HealthService.checkHealth()` |
| `/management/info` | すべて | 認証不要 | `ProfileService.getProfileInfo()` |
| `/management/prometheus` | すべて | 認証不要 | なし |
| `/management/**` | すべて | `ROLE_ADMIN` | `ConfigurationService`、`LogsService`、`MetricsService` |

`/api/account`、`/api/account/change-password` は個別の指定がなく、`/api/**` の「認証済みであること」が適用される。

リソースのメソッドにも `@PreAuthorize` がある。`UserResource` は `hasAuthority("ROLE_ADMIN")`、`AuthorityResource` は `hasAnyAuthority('ROLE_ADMIN')` である（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/UserResource.java`、`src/main/java/io/github/jhipster/sample/web/rest/AuthorityResource.java`）。

## 5. 共通のエラー応答

### 5.1 応答本文の形式

バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/ExceptionTranslator.java` が例外を RFC 7807 の Problem Details に変換する。本文は JSON である。

| № | Lv | 項目名称 | カラム名 | システム属性 | 必須 | 項目説明 | 根拠 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | 種別 | `type` | string | あり | 問題の種別を表す URI。既定は `https://www.jhipster.tech/problem/problem-with-message`。入力検証違反は `https://www.jhipster.tech/problem/constraint-violation` | `ExceptionTranslator`（`getMappedType()`）、`ErrorConstants`、`src/app/shared/jhipster/problem-details.ts` |
| 2 | 1 | タイトル | `title` | string | あり | 問題の種別の短い説明。HTTP ステータスの理由句（例: `Bad Request`）。`BadRequestAlertException` では例外の既定メッセージである | `ExceptionTranslator`（`extractTitle()`）、`src/app/shared/jhipster/problem-details.ts` |
| 3 | 1 | HTTP ステータス | `status` | number | あり | HTTP ステータスコードと同じ値 | 同上 |
| 4 | 1 | 説明 | `detail` | string | 任意 | 発生ごとの説明。例外のメッセージ（原因があれば原因のメッセージ） | 同上 |
| 5 | 1 | 発生箇所 | `instance` | string | 任意 | 発生箇所を表す URI | 同上 |
| 6 | 1 | メッセージキー | `message` | string | あり | 翻訳のメッセージキー。例外に対応づけられたものがなければ `error.http.<ステータス>` | `ExceptionTranslator`（`customizeProblem()` の `MESSAGE_KEY`） |
| 7 | 1 | メッセージのパラメーター | `params` | string | 任意 | エンティティ名（`BadRequestAlertException` の `entityName`） | `ExceptionTranslator`（`buildHeaders()`）、`BadRequestAlertException` |
| 8 | 1 | 要求パス | `path` | string | あり | 要求の URI | `ExceptionTranslator`（`getPathValue()`） |
| 9 | 1 | フィールドエラー | `fieldErrors` | `FieldErrorVM` の配列 | 任意 | 要求本文の `@Valid` による検証違反（`MethodArgumentNotValidException`）のときだけある | `ExceptionTranslator`（`getFieldErrors()`） |
| 10 | 2 | オブジェクト名 | `fieldErrors[].objectName` | string | あり | DTO のクラス名。末尾が `DTO` なら `DTO` を除く | 同上 |
| 11 | 2 | フィールド名 | `fieldErrors[].field` | string | あり | 違反したフィールドの名前 | 同上 |
| 12 | 2 | メッセージ | `fieldErrors[].message` | string | あり | 検証アノテーションの既定メッセージ。なければアノテーションのコード | 同上 |

- `message`、`params`、`path`、`fieldErrors` は Problem Details の拡張メンバーである（RFC 7807 に定義されたメンバーではない）。
- フロントエンドの型は `ProblemDetails`、`ProblemWithMessage`、`FieldErrorVM` である（`src/app/shared/jhipster/problem-details.ts`）。本体からこの型を使っている箇所はなく、`AlertError` は本文を `any` として読む（`src/app/shared/alert/alert-error.ts`）。詳細は [problem-details_DTO設計書](../01_DTO設計書/problem-details_DTO設計書.md) を参照する。
- セキュリティーのフィルター段階での 401 と 403 は、`ExceptionTranslator` を経由しないため本文がない（バックエンドの `SecurityConfiguration` の設定であり、`ExceptionTranslator` はコントローラーで投げられた例外を処理する）。コードからは確認できないため、実行して確かめること。

### 5.2 エラー応答のレスポンスヘッダー

例外が `BadRequestAlertException`（およびそのサブクラスの `EmailAlreadyUsedException`、`LoginAlreadyUsedException`）のとき、`ExceptionTranslator` は失敗アラートのヘッダーを付ける。

| ヘッダー | 値 | 根拠 |
| --- | --- | --- |
| `X-jhipsterSampleApplicationApp-error` | `error.<errorKey>` | `ExceptionTranslator`（`buildHeaders()`）、JHipster ライブラリーの `HeaderUtil.createFailureAlert()` |
| `X-jhipsterSampleApplicationApp-params` | エンティティ名 | 同上 |

`applicationName` はバックエンドの設定 `jhipster.clientApp.name` である。値は `jhipsterSampleApplicationApp`（バックエンドの `src/main/resources/config/application.yml`。各クラスの `@Value` の既定値 `jhipsterSampleApplication` より設定が優先される）。JHipster ライブラリーの `HeaderUtil.createAlert()`、`createFailureAlert()` は `X-` + `applicationName` + `-alert`（`-error`、`-params`）を連結するだけで、大文字と小文字を変えない。したがってバックエンドが付けるヘッダー名は `X-jhipsterSampleApplicationApp-alert`、`X-jhipsterSampleApplicationApp-error`、`X-jhipsterSampleApplicationApp-params` である。HTTP ヘッダー名は大文字と小文字を区別しないため、フロントエンドはすべて小文字の `x-jhipstersampleapplicationapp-error`、`x-jhipstersampleapplicationapp-params` で読む（`src/app/shared/jhipster/constants.ts` の `MESSAGE_ERROR_HEADER_NAME`、`MESSAGE_PARAM_HEADER_NAME`）。ヘッダー名はこの設定から組み立てられるため、設定値を変えるとフロントエンドの定数も合わせて変える必要がある。

フロントエンドは本文ではなくこのヘッダーを先に見る（`src/app/shared/alert/alert-error.ts` の `handleBadRequest()`）。ヘッダーに `errorKey` があれば、その値を翻訳キーとして `error.<errorKey>` の文言をアラートに表示する。

### 5.3 主なエラーと `message`、`errorKey` の対応

| 発生条件 | HTTP ステータス | `type` | `title` | `message` | `errorKey` | 発生箇所 |
| --- | --- | --- | --- | --- | --- | --- |
| 入力検証違反（`@Valid` による要求本文の検証） | 400 | `.../constraint-violation` | `Method argument not valid` | `error.validation` | なし | すべてのコントローラー |
| 制約違反（`@Validated` によるパラメーターの検証。`AccountResource` の `@Email`、`@Size` など） | 400 | `.../constraint-violation` | `Method argument not valid` | `error.validation` | なし | `AccountResource`（クラスに `@Validated` がある）。`UserResource` はクラスに `@Validated` がないため、パスパラメーターの `@Pattern` は働かないと読める |
| 新規登録で `id` が `null` 以外 | 400 | `.../problem-with-message` | `A new <entityName> cannot already have an ID` などの文言 | `error.idexists` | `idexists` | `BankAccountResource`、`LabelResource`、`OperationResource`、`UserResource`、`AuthorityResource` |
| 更新で本文の `id` が `null` | 400 | `.../problem-with-message` | `Invalid id` | `error.idnull` | `idnull` | `BankAccountResource`、`LabelResource`、`OperationResource` |
| 更新でパスの `id` と本文の `id` が違う | 400 | `.../problem-with-message` | `Invalid ID` | `error.idinvalid` | `idinvalid` | 同上 |
| 更新で対象が存在しない | 400 | `.../problem-with-message` | `Entity not found` | `error.idnotfound` | `idnotfound` | 同上 |
| ログイン名が既に使われている | 400 | `.../login-already-used` | `Login name already used!` | `error.userexists` | `userexists` | `UserResource.createUser()`、`UserResource.updateUser()`。登録 (`UserService.registerUser()`) はサービス層の `UsernameAlreadyUsedException` を投げ、`ExceptionTranslator.getProblemDetailWithCause()` が同じ応答に変換する |
| メールアドレスが既に使われている | 400 | `.../email-already-used` | `Email is already in use!` | `error.emailexists` | `emailexists` | `UserResource.createUser()`、`UserResource.updateUser()`、`AccountResource.saveAccount()`、`UserService.registerUser()` |
| パスワードの長さが不正（空、4 文字未満、100 文字超） | 400 | `.../invalid-password` | `Incorrect password` | `error.http.400`（例外に `message` の指定がないため、`ExceptionTranslator` がステータスから組み立てる） | なし | `AccountResource`（`isPasswordLengthInvalid()`）、`InvalidPasswordException` |
| 現在のパスワードが誤っている（パスワード変更） | 400 | `.../invalid-password` | `Incorrect password` | `error.http.400`（同上） | なし | `UserService.changePassword()`（`passwordEncoder.matches()` が `false` のとき）、`InvalidPasswordException` |
| 認証情報の誤り（ログイン失敗） | 401 | 本文なし | － | － | － | `AuthenticateController.authorize()`（`BadCredentialsException`。`ExceptionTranslator.getMappedStatus()` により 401） |
| 権限がない | 403 | `ExceptionTranslator` を経由しないため本文なし（コードからは確認できない） | － | － | － | バックエンドの `SecurityConfiguration` |
| 取得で対象が存在しない | 404 | `ResponseUtil.wrapOrNotFound()` が空の本文を返す（コードからは確認できない） | － | － | － | 各リソースの取得 |
| 同時更新の競合 | 409 | `.../problem-with-message` | ステータスの理由句 | `error.concurrencyFailure` | なし | `ExceptionTranslator.getMappedMessageKey()` と `getMappedStatus()`（`ConcurrencyFailureException`）。ただしバックエンドのコードにこの例外を投げる箇所はなく、エンティティに `@Version` もない（楽観ロックのバージョン列がない）。ライブラリー（Spring Data など）がこの例外を投げたときだけ変換が働くと読める |

根拠は、バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/` 配下の `ExceptionTranslator.java`、`ErrorConstants.java`、`BadRequestAlertException.java`、`EmailAlreadyUsedException.java`、`LoginAlreadyUsedException.java`、`InvalidPasswordException.java`、および各リソースのクラスである。

`<entityName>` はリソースごとに決まっている（`bankAccount`、`label`、`operation`、`adminAuthority`、`userManagement`）。`params` ヘッダーと本文の `params` に入る値である。

`title` の文言（`A new bankAccount cannot already have an ID` など）はリソースごとに異なる。各電文レイアウトのエラーの表に個別に書く。

## 6. 成功通知のレスポンスヘッダー

登録、更新、削除が成功したとき、バックエンドはアラートのヘッダーを付ける。フロントエンドの `notificationInterceptor` がこれを読み、成功のアラートを `AlertService` に追加する（`src/app/core/interceptor/notification.interceptor.ts`）。

| ヘッダー | 値 | 根拠 |
| --- | --- | --- |
| `X-jhipsterSampleApplicationApp-alert` | `<entityName>.created`、`<entityName>.updated`、`<entityName>.deleted`、`userManagement.created` などのメッセージキー | JHipster ライブラリーの `HeaderUtil.createEntityCreationAlert()`、`createEntityUpdateAlert()`、`createEntityDeletionAlert()`、`createAlert()`。呼び出し元は各リソース |
| `X-jhipsterSampleApplicationApp-params` | 登録・更新・削除した対象の ID（またはログイン名、権限名）を URL 符号化した値 | 同上 |

- フロントエンドはすべて小文字の `x-jhipstersampleapplicationapp-alert`、`x-jhipstersampleapplicationapp-params` で読む（`src/app/shared/jhipster/constants.ts` の `MESSAGE_ALERT_HEADER_NAME`、`MESSAGE_PARAM_HEADER_NAME`。ヘッダー名は大文字と小文字を区別しないため一致する）。
- アラートのヘッダーの値が英数字とドットだけからなるときは翻訳キーとして扱い、`alertService.addAlert()` の `translationKey` に渡す。`params` の値は `decodeURIComponent()` で戻し、`translationParams.param` に渡す（`src/app/shared/jhipster/headers.ts` の `getMessageFromHeaders()`）。
- アカウント系の API（`api/register`、`api/activate`、`api/account`、`api/account/change-password`、`api/account/reset-password/*`）と `api/authenticate` は、成功時にアラートのヘッダーを返さない（バックエンドの `AccountResource.java`、`AuthenticateController.java` に `HeaderUtil` の呼び出しがない）。
- 管理 API（`management/*`）もアラートのヘッダーを返さない。

## 7. ページングのレスポンスヘッダーとクエリパラメーター

### 7.1 クエリパラメーター（要求）

ページングのある API は、バックエンドが Spring Data の `Pageable` として受け取る（ライブラリーの動きであり、バックエンドのリポジトリのコードではない）。

| カラム名 | 型 | 既定値 | 項目説明 | 根拠 |
| --- | --- | --- | --- | --- |
| `page` | number | `0` | ページ番号。0 始まり | `src/app/entities/admin/user-management/list/user-management.ts`（`queryBackend()` の `page: pageToLoad - 1`）、`src/app/entities/operation/list/operation.ts`（`links().next`） |
| `size` | number | `20` | 1 ページの件数。フロントエンドは `ITEMS_PER_PAGE`（`20`）を送る | `src/app/config/pagination.constants.ts`（`ITEMS_PER_PAGE`）、上記 2 画面 |
| `sort` | string | なし | `<プロパティー>,<asc または desc>`。複数あるときはカンマ区切りで並べる | `src/app/shared/sort/sort.service.ts`（`buildSortParam()`） |

- `size` の既定値 `20` は Spring Data の既定値である（ライブラリーの仕様であり、本リポジトリのコードには現れない）。フロントエンドが `size` を送らない API（`api/users`、`api/bank-accounts`、`api/labels` を引数なしで呼ぶとき）では、この既定値が適用されると読める。
- バックエンドが並び替えに使えるプロパティーを制限している API がある。`api/admin/users` と `api/users` は、`sort` に許可されていないプロパティーが含まれると 400 を返す（バックエンドの `UserResource.java`、`PublicUserResource.java` の `ALLOWED_ORDERED_PROPERTIES`、`onlyContainsAllowedProperties()`）。許可されるプロパティーは各電文レイアウトに書く。
- `createRequestOption()` は、値が `undefined`、`null`、空文字列のものを送らない（`src/app/core/request/request-util.ts`）。

### 7.2 レスポンスヘッダー（応答）

ページングのある API は、バックエンドが JHipster ライブラリーの `PaginationUtil.generatePaginationHttpHeaders()` で次のヘッダーを付ける。ページングのある API は `api/admin/users`、`api/operations`、`api/users` の 3 つである（バックエンドの各リソースで `generatePaginationHttpHeaders()` を呼んでいるのはこの 3 つ）。

| ヘッダー | 値の例 | 項目説明 | 根拠 |
| --- | --- | --- | --- |
| `X-Total-Count` | `42` | 全件数 | ライブラリーの `PaginationUtil`、`src/app/config/pagination.constants.ts`（`TOTAL_COUNT_RESPONSE_HEADER`） |
| `Link` | `<...?page=0&size=20>; rel="last",<...?page=0&size=20>; rel="first"` | ページへのリンク。`rel` は `first`、`last`、`next`、`prev` | ライブラリーの `PaginationUtil`（`Link` と `LinkHeaderUtil`）、`src/app/shared/jhipster/link-header.ts` |

- フロントエンドの読み取り方は画面ごとに違う。ユーザ管理の一覧は `X-Total-Count` を読み、`ngb-pagination` でページを切り替える（`src/app/entities/admin/user-management/list/user-management.ts` の `fillComponentAttributesFromResponseHeader()`）。取引の一覧は `Link` を `ParseLinks.parseAll()` で解析し、`next` があれば無限スクロールで次のページを読む（`src/app/entities/operation/list/operation.ts` の `fillComponentAttributesFromResponseHeader()`、`queryBackend()`）。
- ページングのある API を `HttpClient` の `observe: 'response'` で呼んだときは、画面は `HttpResponse.headers` から読む。`httpResource` で呼んだときは `headers()` シグナルから読む。

## 8. フロントエンドの共通処理（インターセプター）

`app.config.ts` は 4 つのインターセプターをこの順で登録する（`src/app/app.config.ts` の `withInterceptors()`）。

| No. | インターセプター | 処理 | 根拠 |
| --- | --- | --- | --- |
| 1 | `authInterceptor` | 保存されたトークンを `Authorization` ヘッダーに付ける | `src/app/core/interceptor/auth.interceptor.ts` |
| 2 | `authExpiredInterceptor` | 401 のとき、URL に `api/account` を含まなければ、現在の URL を保存し、ログアウトして `/login` へ遷移する | `src/app/core/interceptor/auth-expired.interceptor.ts` |
| 3 | `errorHandlerInterceptor` | エラーをイベント `jhipsterSampleApplicationApp.httpError` として配信する（401 で、かつ `message` が空か URL に `api/account` を含むときは配信しない） | `src/app/core/interceptor/error-handler.interceptor.ts` |
| 4 | `notificationInterceptor` | 成功応答のアラートヘッダーを読み、成功のアラートを追加する | `src/app/core/interceptor/notification.interceptor.ts` |

`AlertError` はイベントを受け取り、ステータスに応じた文言を `<jhi-alert-error />` に表示する（`src/app/shared/alert/alert-error.ts` の `handleHttpError()`）。

| HTTP ステータス | 表示 | 根拠 |
| --- | --- | --- |
| 0（サーバーに到達できない） | 「Server not reachable」（翻訳キー `error.server.not.reachable`） | 同上、`src/i18n/en/global.json` |
| 400 | レスポンスヘッダーの `error`、または本文の `message`、`fieldErrors` を使う | 同上（`handleBadRequest()`） |
| 404 | 「Not found」（翻訳キー `error.url.not.found`） | 同上、`src/i18n/en/global.json` |
| 401（`api/account` を含む URL） | 何も表示しない（`errorHandlerInterceptor` が配信しないため） | `src/app/core/interceptor/error-handler.interceptor.ts` |
| 400 以外の上記以外 | 本文の `detail`、`message`、`params` を使う | 同上（`handleDefaultError()`） |

本文の `fieldErrors` があるときは、フィールドごとに「Error on field "<フィールド名>"」と、`error.<message>` の文言を表示する（`handleFieldsError()`）。`message` が `Min`、`Max`、`DecimalMin`、`DecimalMax` のときは `Size` に置き換える。
