## 2. 単項目チェック

| No. | 項目 | チェック内容 | 必須 | 最大長 / 形式 | エラーメッセージ (翻訳キー) | 根拠 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Filter | チェックなし。必須チェックも形式チェックもなく、バリデーターは登録していない。入力値は画面の中で絞り込みに使うだけで、サーバーへの送信なし | 任意 | 最大長のチェックはなし（`maxlength` 属性もバリデーターもない）。文字種の制限もなし | －（エラーメッセージなし） | `src/app/admin/logs/logs.html`（`id="logs-filter"`）、`src/app/admin/logs/logs.ts`（`readonly filter = signal('')`） |

補足:

- 入力欄の形: `<input id="logs-filter" type="text" [ngModel]="filter()" (ngModelChange)="filter.set($event)" class="form-control" />` である。`<form>` の中になく、`name` 属性もない。`FormsModule` の `ngModel` で、値をシグナル `filter` と双方向に結び付けている。`FormGroup` に属さないため、`invalid`、`dirty`、`touched` の状態も持たない。
- バリデーター: この入力欄にはバリデーターが 1 つも付いていない。`Validators.required`、`Validators.maxLength`、`Validators.pattern` のいずれもなく、テンプレートにバリデーターを指定する属性もない。エラーメッセージを表示する分岐もない。
- 絞り込みの動き: 入力のたびに `filteredAndOrderedLoggers`（`computed`）が再計算される。`filter()` が空文字（初期値 `''`）なら絞り込まない。空文字でなければ、`logger.name.toLowerCase().includes(filter.toLowerCase())` が真のロガーだけを残す。部分一致であり、大文字と小文字は区別しない。前後の空白は取り除かず、ワイルドカードなどの記号も特別に扱わない。
- 対象: 絞り込みの対象はロガー名（`Log` の `name`）だけである。レベル（`level`）では絞り込まない。
- 該当なしのとき: どのロガーも一致しなければ、表の行は 0 件になる。「該当なし」を知らせる文言はない。
- 件数の文言: 「There are {{ total }} loggers.」の `total` は `loggers()?.length`（絞り込み前の件数）である。絞り込んでもこの数は変わらない。
- 並び替えとの関係: 絞り込みのあとに、`sortState` の並び替えが適用される。
- 再取得との関係: レベルを変更したあとの一覧の再取得でも、シグナル `filter` と `sortState` は保たれる。
- サーバーへの送信: 入力値を要求に含めない。絞り込みによって API を呼び直すこともない。
- URL と初期状態: 入力値をクエリパラメーターに反映しない。画面を読み込み直すと `filter` は初期値 `''` に戻る。

## 4. サーバ側チェック

この画面の入力値（絞り込みの文字列）はサーバーに送らない。サーバーが受け取るのは、ロガーの一覧の取得（`GET management/loggers`）と、レベルの変更（`POST management/loggers/{name}`）のパスパラメーター `name` と本文の `configuredLevel` である。この画面はボタンに書いてある 6 つのレベル名だけを送り、ロガー名は一覧の応答から使う。

画面には HTTP エラーを表示する仕組みがない（テンプレートに `<jhi-alert-error />` がない）。要求の失敗と、画面に現れる影響は次のとおりである。

| No. | 発生条件（バックエンド） | HTTP ステータス | バックエンドの応答 | 画面の表示 | この画面から発生するか |
| --- | --- | --- | --- | --- | --- |
| 1 | レベル変更の要求の値が不正である（本文の `configuredLevel` がレベルに変換できない値、パスパラメーターのロガー名がない） | 400 | コードからは確認できない | 処理なし（一覧の再取得も、エラーの表示もなし） | 発生しない（ボタンは `TRACE`、`DEBUG`、`INFO`、`WARN`、`ERROR`、`OFF` の 6 つだけを送り、ロガー名は `GET management/loggers` の応答の `loggers` のキーだけを使う） |
| 2 | トークンがない、またはトークンが無効 | 401 | － | `authExpiredInterceptor` が現在の URL を保存してログアウトし、`/login` へ遷移する | トークンが無効になったとき |
| 3 | `ROLE_ADMIN` を持たないユーザーのトークン（バックエンドは `/management/**` に `ROLE_ADMIN` を要求） | 403 | － | エラーの表示なし。取得の失敗なら `loggers` は空配列になり、「There are 0 loggers.」と行のない表になる。変更の失敗なら画面は変化なし | 通常は発生しない（ルートガードが `ROLE_ADMIN` を持たないユーザーを `/accessdenied` へ遷移させる） |
| 4 | サーバーに到達できない | 0 | － | エラーの表示なし。画面の状態は行番号 3 と同じ | 発生し得る |
| 5 | 上記以外の失敗 | 500 など | － | エラーの表示なし。画面の状態は行番号 3 と同じ | コードからは確認できない |

補足:

- バックエンドの認可は、バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java` による。401、403 のときの応答の本文は Spring Security のライブラリーの動きであり、コードからは確認できない。
- ログのエンドポイントは Spring Boot Actuator（ライブラリー）であり、バックエンドのリポジトリにソースはない。要求の値が不正なときに 400 を返すのはライブラリーの動きであり、実機では確認していない。
- ロガー名について: 一覧にないロガー名を送った場合のバックエンドの動きはライブラリーの動きであり、コードからは確認できない。この画面は一覧の応答にあるロガー名だけを送る。
- `errorHandlerInterceptor` は HTTP エラーをイベント `jhipsterSampleApplicationApp.httpError` として配信するが、この画面にはそれを購読して表示する `<jhi-alert-error />` がない。サーバーに到達できないときも、共通部品の「Server not reachable」は表示されない。共通部品の動きは [HTTP共通処理_画面設計書](../../共通/HTTP共通処理/HTTP共通処理_画面設計書.md) に書く。
- 401 のときの `authExpiredInterceptor` の動き（現在の URL を `StateStorageService.storeUrl()` で保存し、ログアウトして `/login` へ遷移する）は、取得と変更のどちらの要求でも同じである。
