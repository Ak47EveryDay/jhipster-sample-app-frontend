## 2. 機能概要

- 認可の確認は 2 つの階層で行う。
  - ルートの単位: ガード `userRouteAccessService` が、ルートに入る前にログインと権限を確認する。
  - 画面の一部の単位: ディレクティブ `jhiHasAnyAuthority` が、権限に応じて要素を出すかどうかを決める。この確認は表示だけを制御し、ルートに入れるかどうかは決めない。
- ガードはルート定義の `canActivate: [userRouteAccessService]` で登録する。必要な権限はルートの `data.authorities` に配列で指定する。`data.authorities` がなければ、ログインしていることだけを確認する。
- 未ログインなら、要求された URL を保存して `/login` へ遷移する。ログインし直せば元の画面へ戻る。
- 権限が足りなければ `/accessdenied` へ遷移する。
- ガードは API として `GET api/account` を呼ぶ（`AccountService.identity()`。キャッシュがあれば呼ばない）。
- 権限の値は `Authority.ADMIN`（`'ROLE_ADMIN'`）と `Authority.USER`（`'ROLE_USER'`）である。

## 3. 画面レイアウト

この部品は画面を持たない。ガードの流れは次のとおりである。

```
ガード付きルートへの遷移
    → userRouteAccessService(next, state)
        → accountService.identity()                … GET api/account（キャッシュがあれば HTTP なし）
        → アカウントなし（未ログイン）
              stateStorageService.storeUrl(state.url)
              router.navigate(['/login'])          … false を返して遷移を中止
        → アカウントあり
              data.authorities がない、空、または hasAnyAuthority() が true
                  true を返して通す
              それ以外
                  router.navigate(['accessdenied']) … false を返して遷移を中止
```

## 5. イベント処理

### 5.1 イベント一覧

| No. | イベント発生源 | イベント | 遷移先 | イベント物理名 |
| --- | --- | --- | --- | --- |
| 1 | ガード付きルートへの遷移 | 未ログインであった | ログイン（`/login`） | `stateStorageService.storeUrl(state.url)`、`router.navigate(['/login'])` |
| 2 | ガード付きルートへの遷移 | 権限が足りなかった | アクセス拒否（`/accessdenied`） | `router.navigate(['accessdenied'])` |
| 3 | ガード付きルートへの遷移 | ログインしており、権限も満たしていた | なし（遷移を続ける） | `map()` の中の `return true` |
| 4 | 画面の表示（`jhiHasAnyAuthority` を持つ要素） | アカウントまたは権限が変わった | なし | `HasAnyAuthorityDirective` の `effect()` |
| 5 | ナビゲーション中のエラー | エラーの `status` が 403 | アクセス拒否（`/accessdenied`） | `withNavigationErrorHandler`（`src/app/app.config.ts`） |

### 5.2 イベント詳細

#### 5.2.1 ガードの判定

- トリガー: `canActivate: [userRouteAccessService]` を持つルートへ遷移しようとすること。
- 処理手順:
  1. `inject(AccountService)`、`inject(Router)`、`inject(StateStorageService)` で依存を取り、`accountService.identity()` を呼ぶ（[アカウント状態と認証_画面設計書](../アカウント状態と認証/アカウント状態と認証_画面設計書.md) の 5.2.1）。
  2. `identity()` は失敗を `null` に変えて返す。結果は `map()` で判定する。
  3. アカウントがあるときは、ルートの `next.data` から `authorities` を取り出す。
     - `authorities` がないか、長さが 0 なら `true` を返す。
     - `accountService.hasAnyAuthority(authorities)` が `true` なら `true` を返す。
     - どちらでもなければ、開発モード（`isDevMode()`）のときは `console.error('User does not have any of the required authorities:', authorities)` を出し、`router.navigate(['accessdenied'])` を実行して `false` を返す。
  4. アカウントがないときは、`stateStorageService.storeUrl(state.url)` で要求された URL を保存し、`router.navigate(['/login'])` を実行して `false` を返す。
- 状態変化: アカウントのキャッシュ（`identity()` が HTTP を呼んだ場合）、sessionStorage の `previousUrl`（未ログインのとき）。
- 遷移: 未ログインなら `/login`、権限が足りなければ `/accessdenied`。どちらもガードが自ら遷移させ、元の遷移は中止される。
- 補足:
  - `data.authorities` は親ルートにだけ指定できる。管理画面は親の `path: 'admin'` に `[Authority.ADMIN]` があり、子の 5 ルートはそれを引き継ぐ。
  - 未ログインで保存された URL は、ログイン後の `AccountService.navigateToStoredUrl()` で使われる。`POST api/authenticate` が 401 で失敗したときは `authExpiredInterceptor` が保存する URL を `/login` で上書きすると読める（[HTTP共通処理_画面設計書](../HTTP共通処理/HTTP共通処理_画面設計書.md) 参照）。
  - `/login` 自身はガードを持たない。ログイン済みで `/login` を開いたときは、`Login.ngOnInit()` がホームへ遷移させる。

#### 5.2.2 権限による表示の制御（`jhiHasAnyAuthority`）

- トリガー: ディレクティブが付いた要素の描画、またはアカウントと権限の入力値の変化。
- 処理手順:
  1. `computed()` で `hasPermission` を作る。アカウントに `authorities` があり、かつ `accountService.hasAnyAuthority(this.authorities())` が `true` のときに `true` になる。
  2. `effect()` の中で、`hasPermission()` が `true` なら `viewContainerRef.createEmbeddedView(templateRef)` で要素を描き、`false` なら `viewContainerRef.clear()` で除く。
- 状態変化: 要素の表示と非表示。
- 遷移: なし。
- 補足:
  - 未ログインのときはアカウントが `null` であるため、`hasPermission` は `undefined` となり、要素は表示されないと読める。
  - これは表示の制御である。URL を直接開くことを防ぐわけではなく、防ぐのはルートガードである。
  - 使っているのはナビゲーションバーの「Administration」メニューの 1 か所だけである（`*jhiHasAnyAuthority="'ROLE_ADMIN'"`、`src/app/layouts/navbar/navbar.html`）。

#### 5.2.3 ナビゲーション中のエラー（403）

- トリガー: ナビゲーションが `NavigationError` で失敗し、エラーの `status` が 403 であること。
- 処理手順: `withNavigationErrorHandler`（`src/app/app.config.ts`）が `router.navigate(['/accessdenied'])` を実行する。
- 遷移: アクセス拒否（`/accessdenied`）。
- 補足: ガードやリゾルバーが自前で遷移するため、このハンドラーが 403 で動く場面はコードからは確認できない。詳細は [エラー画面_画面設計書](../エラー画面/エラー画面_画面設計書.md) に書く。

### 5.3 API呼び出し一覧

| No. | 目的 | メソッド | パス | 要求パラメーター | 応答 | 成功時 | エラー時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | アカウントの取得（ガードの判定のため） | GET | `api/account` | なし | 200: `Account`（`authorities` を使う） | アカウントがあるかどうかで判定する | `identity()` が `null` を返すため、未ログインとして `/login` へ遷移する |

補足:

- ガードは自身では HTTP を送らない。`AccountService.identity()` が送り、キャッシュ（`shareReplay()`）があれば送らない。
- 未ログインのとき `GET api/account` は 401 になる。URL に `api/account` を含む 401 は `authExpiredInterceptor` の対象外であるため、ログアウトの処理は起きず、ガードの `router.navigate(['/login'])` だけで遷移する。
- バックエンド側でも認可を確認している。`/api/admin/**` は `ROLE_ADMIN` を、`/api/**` は認証を要求する（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）。ガードは画面の遷移を制御するものであり、バックエンドの認可の代わりにはならない。

### 5.4 画面遷移

| 遷移先 | 条件 | トリガー |
| --- | --- | --- |
| ログイン（`/login`） | 未ログインのままガード付きルートを開いた | `router.navigate(['/login'])`（要求された URL を `stateStorageService.storeUrl()` で保存してから遷移する） |
| アクセス拒否（`/accessdenied`） | ログインしているが、ルートの `data.authorities` に自分の権限がない | `router.navigate(['accessdenied'])` |

### 5.5 利用箇所

- `userRouteAccessService` を登録しているルート定義は、`src/app/app.routes.ts`、`src/app/account/password/password.route.ts`、`src/app/account/settings/settings.route.ts`、`src/app/entities/bank-account/bank-account.routes.ts`、`src/app/entities/label/label.routes.ts`、`src/app/entities/operation/operation.routes.ts`、`src/app/entities/admin/user-management/user-management.routes.ts`、`src/app/entities/admin/authority/authority.routes.ts` の 8 ファイルである。
- `HasAnyAuthorityDirective` を import しているのは `src/app/layouts/navbar/navbar.ts` だけである。
- ログイン・登録・アカウント有効化・パスワード再設定の画面に権限による表示の制御はない。

### 5.6 内部構造

- ガードはクラスではなく関数（`CanActivateFn`）である。引数は `next`（`ActivatedRouteSnapshot`）と `state`（`RouterStateSnapshot`）である。戻り値は `Observable<boolean>` である。
- `hasAnyAuthority(authorities)`（`src/app/core/auth/account.service.ts`）は、アカウントの `authorities` のうち引数に含まれるものが 1 つでもあれば `true` を返す。引数が文字列なら配列にする。
- `data.authorities` の指定の仕方は 2 通りある。管理画面は列挙型（`[Authority.ADMIN]`）で、ユーザ管理と権限は文字列（`['ROLE_ADMIN']`）で書いている。値は同じ `'ROLE_ADMIN'` である。
