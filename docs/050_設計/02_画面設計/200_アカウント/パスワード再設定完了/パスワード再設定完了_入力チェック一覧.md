補足:

- エラーメッセージの表示条件: 各コントロールが `invalid` で、かつ `dirty` または `touched` のときだけメッセージのブロックを表示する（例: `newPasswordRef.invalid && (newPasswordRef.dirty || newPasswordRef.touched)`）。
- 行番号 7 の表示条件: クエリパラメーターの購読が始まって `initialized` が `true` になり、かつ `key` が空のときである。
- 送信ボタンとの関係: Validate new password ボタンは `[disabled]="passwordForm.invalid"` の間は無効である。行番号 1 から 6 のいずれかのエラーがあると押せない。`finishReset()` には、単項目の入力値を確認する処理は書かれていない。
- パスワード強度バー: New password の下に `<jhi-password-strength-bar>` を表示するが、強度はチェックではない。強度が低くてもフォームは有効である。動きの詳細は [パスワード変更_画面設計書](../パスワード変更/パスワード変更_画面設計書.md) の 5.2.2 に書く。
- ブラウザーの標準の検証: `<form>` に `novalidate` の明示はないが、Angular は `[formGroup]` を持つ `<form>` 要素に `novalidate` を設定するため、ブラウザー自身の検証メッセージは使わない（Angular の標準の動きであり、本リポジトリのコードではない）。
- 初期状態: 2 つのコントロールとも空文字列なので、最初は必須エラーの状態でフォームは無効である。`dirty` も `touched` も立っていないため、メッセージは表示されない。

## 4. サーバ側チェック

`POST api/account/reset-password/finish` が失敗したとき、`PasswordResetFinish.finishReset()` の `error` はエラーの内容を見ずに `error` を `true` にする。この画面に `<jhi-alert-error />` はないため、表示は HTTP ステータスによらず「Your password couldn't be reset.」の 1 種類である。失敗しても画面は遷移せず、フォームと入力値は残る。

| No. | 発生条件（バックエンド） | HTTP ステータス | バックエンドの応答 | 画面の表示 | この画面から発生するか |
| --- | --- | --- | --- | --- | --- |
| 1 | リセットキーに一致するユーザーがない、またはリセット日時から 1 日以上経過している（`AccountResource.finishPasswordReset()` が `AccountResourceException` を投げる） | 400 | Problem Details。`title` は `Account resource request invalid`、`message` は `error.http.400` | 「Your password couldn't be reset. Remember a password request is only valid for 24 hours.」（翻訳キー `reset.finish.messages.error`） | 発生し得る（メールの送信から 24 時間以上経った場合、同じキーを 2 度使った場合、依頼し直したことで前に届いたメールのキーが無効になった場合） |
| 2 | 新しいパスワードが空、4 文字未満、または 100 文字超（`AccountResource.isPasswordLengthInvalid()`） | 400 | Problem Details。`type` は `https://www.jhipster.tech/problem/invalid-password`、`title` は `Incorrect password` | 同上 | 通常は発生しない（行番号 1 から 3 のチェックと Validate new password ボタンの無効化で送信できない） |
| 3 | サーバーに到達できない | 0 | － | 同上（`<jhi-alert-error />` がないため `error.server.not.reachable` は表示されない） | 発生し得る |
| 4 | 上記以外の失敗 | 500 など | － | 同上 | コードからは確認できない |

補足:

- バックエンド側の定義は次のとおりである。
  - `AccountResource.finishPasswordReset()` は、本文を `KeyAndPasswordVM`（`key`、`newPassword`）として受け取る。`@Valid` も制約の注釈もない（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/AccountResource.java`、`src/main/java/io/github/jhipster/sample/web/rest/vm/KeyAndPasswordVM.java`）。
  - 長さのチェックは `AccountResource.isPasswordLengthInvalid()` である。画面の上限は 50 であるのに対し、バックエンドの上限は 100 である。
  - キーの検索は `UserService.completePasswordReset(newPassword, key)` である（バックエンドの `src/main/java/io/github/jhipster/sample/service/UserService.java`）。`findOneByResetKey(key)` で探し、`user.getResetDate().isAfter(Instant.now().minus(1, ChronoUnit.DAYS))` で 1 日以内かを確かめる。条件を満たせば `resetKey` と `resetDate` を `null` にする。
  - `AccountResourceException` は、例外クラスの `@ResponseStatus` により 400 になる（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/ExceptionTranslator.java` の `toStatus()`）。メソッドのコメントには 500 と書かれているが、コード上のステータスは 400 である。
  - バックエンドのテスト `src/test/java/io/github/jhipster/sample/web/rest/AccountResourceIT.java` は、成功で 200、新しいパスワードが `foo` の 3 文字の場合とリセットキーが誤っている場合に 400 を検証している。
- 行番号 1 の 400 の Problem Details をそのまま表示する `<jhi-alert-error />` はこの画面にない。画面に表示されるのは画面独自の危険アラートだけである。
- 401 について: バックエンドはこの API を認証なしで受け付けるため（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）、画面から 401 を発生させる経路はコード上にない。
- エラー時の共通の動き: 失敗しても画面は遷移せず、Validate new password ボタンは無効にならない（要求中も無効にする指定がない）。フォームの値は変更しない。
