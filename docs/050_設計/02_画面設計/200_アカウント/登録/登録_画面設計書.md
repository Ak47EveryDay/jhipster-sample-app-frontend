## 2. 機能概要

- ユーザー名、メールアドレス、パスワード、パスワードの確認を入力して、新しいユーザーを登録する。入力値は `Registration`（`login`、`email`、`password`、`langKey`）として `POST api/register` に送る。確認用のパスワードは送らない。
- 登録に成功するとフォームを隠し、「Registration saved!」の成功アラートを表示する。画面は遷移しない。ログインは、バックエンドが送る有効化メールのリンクでアカウントを有効化したあとに行う。
- ログイン ID またはメールアドレスが既に使われているときは、それぞれ別の危険アラートを表示する。それ以外の失敗では「Registration failed!」の危険アラートを表示する。失敗したときはフォームにとどまる。
- パスワードと確認用のパスワードが一致しないときは要求を送らず、「The password and its confirmation do not match!」の危険アラートを表示する。
- Username、Email、New password、New password confirmation は必須である。フォームが無効な間は Register ボタンが無効になる。
- New password の下にパスワード強度バーを表示する。強度は表示するだけで、フォームの妥否には影響しない。
- 画面を開くと Username 入力欄にフォーカスする。
- この画面には `<jhi-alert-error />` と `<jhi-alert />` はない。HTTP エラーは画面独自のアラートで表示する。

## 3. 画面レイアウト

画面は `Main` の `<router-outlet />` の中、`<div class="card jh-card">` の内側に表示される（`src/app/layouts/main/main.html`）。テンプレートのルートは `<div>` で、その中に中央寄せの `<div class="d-flex justify-content-center">` と `<div class="col-md-8">` の組が 2 つある。1 つ目に見出しとアラート、2 つ目にフォームとリンクを置く。上から順に次の領域が占める。

```
見出し領域（<h1 data-cy="registerTitle">）
    Registration
アラート領域
    Registration saved! Please check your email for confirmation.   … success()
    Registration failed! Please try again later.                     … error()
    Login name already registered! Please choose another one.        … errorUserExists()
    Email is already in use! Please choose another one.              … errorEmailExists()
    The password and its confirmation do not match!                  … doNotMatch()
入力フォーム領域（<form name="form">）                              … !success() のとき
    Username                   … テキストボックス
    Email                      … メール入力欄
    New password               … パスワードボックス、パスワード強度バー
    New password confirmation  … パスワードボックス
ボタン領域
    [Register]
リンク領域（<div class="mt-3 alert alert-warning">）
    If you want to [sign in], you can try the default accounts: ...
```

| 領域 | テンプレート上の要素 | 表示条件 | 4 章の対応 |
| --- | --- | --- | --- |
| 見出し領域 | `<h1 data-cy="registerTitle" jhiTranslate="register.title">` | 常に | `### 見出し領域` |
| アラート領域 | 成功アラート、失敗アラート、ログイン ID 重複、メールアドレス重複、パスワード不一致の各 `<div>`（成功は `class="alert alert-success"`、ほかは `class="alert alert-danger"`） | 各シグナルが `true` のとき | `### アラート領域` |
| 入力フォーム領域 | `<form name="form" (ngSubmit)="register()" [formGroup]="registerForm">` の中の 4 つの `<div class="mb-3">` | `!success()` | `### 入力フォーム領域` |
| ボタン領域 | Register ボタン | `!success()`（フォームの中にある） | `### ボタン領域` |
| リンク領域 | `<div class="mt-3 alert alert-warning">`（`sign in` リンクを含む案内） | 常に | `### リンク領域` |

### 5.2 イベント詳細

#### 5.2.1 画面初期化

- トリガー: `/account/register` への遷移。ルートに `canActivate` も `resolve` もなく、コンポーネントに `ngOnInit()` もないため、API を呼ばない。
- 処理手順:
  1. フィールド初期化で `registerForm` ができる。4 つのコントロールの初期値はすべて空文字列である。`login`、`email`、`password`、`confirmPassword` は必須のため、この時点のフォームは無効で、Register ボタンは無効である。
  2. `ngAfterViewInit()` が `this.login().nativeElement.focus()` で Username 入力欄にフォーカスする。
- 状態変化: なし（`success`、`error`、`errorEmailExists`、`errorUserExists`、`doNotMatch` はすべて `false` のまま）。
- 遷移: なし。

#### 5.2.2 入力（Username、Email、New password、New password confirmation）

- トリガー: 各入力欄への入力。
- 処理手順: Reactive Forms がコントロールの値を更新し、バリデーターを評価し直す。この画面には入力時のメソッド呼び出しはない。
- 状態変化: `registerForm` の各コントロールの値と、`invalid`、`dirty`、`touched` の状態。
- 表示の変化: 各入力欄の下に、コントロールが `invalid` で、かつ `dirty` または `touched` のときだけメッセージのブロックを表示する。表示する文言はエラーの種類ごとに次のとおりである。
  - Username: `loginRef.errors?.required` なら翻訳キー `register.messages.validate.login.required`、`minlength` なら `register.messages.validate.login.minlength`、`maxlength` なら `register.messages.validate.login.maxlength`、`pattern` なら `register.messages.validate.login.pattern`。
  - Email: `emailRef.errors?.required` なら翻訳キー `global.messages.validate.email.required`、`email` なら `global.messages.validate.email.invalid`、`minlength` なら `global.messages.validate.email.minlength`、`maxlength` なら `global.messages.validate.email.maxlength`。
  - New password: `passwordRef.errors?.required` なら翻訳キー `global.messages.validate.newpassword.required`、`minlength` なら `global.messages.validate.newpassword.minlength`、`maxlength` なら `global.messages.validate.newpassword.maxlength`。
  - New password confirmation: `confirmPasswordRef.errors?.required` なら翻訳キー `global.messages.validate.confirmpassword.required`、`minlength` なら `global.messages.validate.confirmpassword.minlength`、`maxlength` なら `global.messages.validate.confirmpassword.maxlength`。
  - 1 つの入力欄で複数のエラーが同時に立つときは、メッセージを並べて表示する。
- パスワード強度バー `<jhi-password-strength-bar>`（`PasswordStrengthBar`、`src/app/account/password/password-strength-bar/password-strength-bar.ts`）の動き:
  - 入力 `passwordToCheck`（既定値は空文字列）に New password のコントロールの値（`passwordRef.value`）を渡す。
  - テンプレートは「Password strength:」の文言と、`<ul id="strengthBar">` の 5 つの `<li class="point">` である。各 `li` は幅 20px、高さ 5px で、既定の背景色は `#ddd` である（`password-strength-bar.scss`）。
  - `constructor` の `effect` が `passwordToCheck()` を読む。値が空のときは何もしない（色は前の表示のまま）。値があれば `measureStrength()` で強度を数値にし、`getColor()` で色と個数を決める。ホスト要素にクラスがあれば取り除いたあと、先頭からその個数の `li` に色を付け、残りを `#DDD` にする。
  - `measureStrength(p)`: 小文字（`/[a-z]+/`）、大文字（`/[A-Z]+/`）、数字（`/\d+/`）、記号（変数 `regex` の正規表現）の 4 種類のうち、含む種類の数を `passedMatches`（0 から 4）とする。`force` の初期値は 0 で、これに `2 * p.length + (p.length >= 10 ? 1 : 0)` と `passedMatches * 10` を加える。次の上限を上から順に適用する。
    - `p.length` が 6 以下なら `force` の上限は 10 である。
    - `passedMatches` が 1 なら上限は 10、2 なら上限は 20、3 なら上限は 40 である。
  - `getColor(s)`: `s` が 10 以下なら 1 個（`#F00`）、10 を超え 20 以下なら 2 個（`#F90`）、20 を超え 30 以下なら 3 個（`#FF0`）、30 を超え 40 以下なら 4 個（`#9F0`）、40 を超えれば 5 個（`#0F0`）である。
  - 強度バーは表示だけである。強度によってフォームを無効にすることはなく、強度の値を送信することもない。例と計算は [パスワード変更_画面設計書](../パスワード変更/パスワード変更_画面設計書.md) の 5.2.2 に書く。
- 遷移: なし。

#### 5.2.3 Register ボタンクリック（登録）

- トリガー: Register ボタン（`type="submit"`）によるフォームの送信（`(ngSubmit)="register()"`）。ボタンは `registerForm.invalid` の間は無効である。
- 処理手順:
  1. `register()` は最初に `doNotMatch`、`error`、`errorEmailExists`、`errorUserExists` を `false` にする。
  2. `this.registerForm.getRawValue()` から `password` と `confirmPassword` を取り出し、`===` で比較する。
  3. 一致しなければ `this.doNotMatch.set(true)` にして終わる。要求は送らない。
  4. 一致すれば `login`、`email` を取り出し、`this.registerService.save({ login, email, password, langKey })` を購読する。`langKey` は `this.translateService.getCurrentLang() ?? 'en'` である。`RegisterService.save()` は `POST api/register` を送る。
  5. 成功（`next`）: `this.success.set(true)` にする。テンプレートは `@if (!success())` のフォームを隠し、成功アラートを表示する。遷移はしない。フォームの値は消さない。
  6. 失敗（`error`）: `processError(response)` が応答を見て、いずれか 1 つのシグナルを `true` にする。フォームは表示されたまま、入力値も残る。
     - `response.status === 400` で、`response.error.type === LOGIN_ALREADY_USED_TYPE` のとき: `errorUserExists` を `true` にする。
     - `response.status === 400` で、`response.error.type === EMAIL_ALREADY_USED_TYPE` のとき: `errorEmailExists` を `true` にする。
     - それ以外: `error` を `true` にする。
- パスワードの一致チェックについて: バリデーターではなく `register()` の中の比較である。2 つの入力欄が異なっていてもフォームは有効なので Register ボタンは押せる。比較は送信のたびに行われ、入力中には行わない。
- トークンとアカウントの状態: 登録ではトークンを保存せず、`AccountService` のアカウントも変えない。登録が成功してもログイン状態にはならない。
- HTTP エラーの共通処理: `errorHandlerInterceptor` は失敗をイベント `jhipsterSampleApplicationApp.httpError` として配信するが、この画面に `<jhi-alert-error />` はないため、配信された内容は表示されない。`authExpiredInterceptor` は 401 のときだけ動くが、`POST api/register` はバックエンドが認証を要求しないため、コード上は起こらない。
- バックエンドの動き（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/AccountResource.java`、`registerAccount()`）:
  - 本文を `@Valid @RequestBody ManagedUserVM` で受け取る。パスワードが空、4 文字未満、100 文字超のいずれかなら `InvalidPasswordException`（400）を投げる。
  - `UserService.registerUser()`（バックエンドの `src/main/java/io/github/jhipster/sample/service/UserService.java`）は、小文字にしたログイン ID と、大文字と小文字を区別しないメールアドレスで既存のユーザーを探す。見つかったユーザーが有効化済みなら、ログイン ID なら `UsernameAlreadyUsedException`、メールアドレスなら `EmailAlreadyUsedException` を投げる（どちらも 400。ログイン ID を先に調べる）。見つかったユーザーが未有効化なら、そのユーザーを削除して登録を続ける。
  - 新しいユーザーは、ログイン ID とメールアドレスを小文字にして保存する。`activated` は `false`、有効化キーは生成した値、権限は `ROLE_USER` である。フロントエンドは `firstName`、`lastName`、`imageUrl` を送らないため、これらは `null` のまま保存される。
  - 保存後、`MailService.sendActivationEmail(user)` で有効化メールを送る（`@Async` による非同期送信。送信に失敗しても警告ログを出すだけで応答は変わらない）。メールのリンクは `<baseUrl>/account/activate?key=<有効化キー>` である（バックエンドの `src/main/resources/templates/mail/activationEmail.html`）。`baseUrl` はバックエンドの設定 `jhipster.mail.base-url` である。
  - 成功すると 201 を返す。本文もアラートのヘッダーもない。
- 未有効化のユーザーの削除: バックエンドの `UserService.removeNotActivatedUsers()` が、作成から 3 日経過した未有効化のユーザーを毎日 01:00 に削除する（`@Scheduled(cron = "0 0 1 * * ?")`）。
- 状態変化: `doNotMatch`、`error`、`errorEmailExists`、`errorUserExists`、`success`。
- 遷移: なし。

#### 5.2.4 sign in リンククリック

- トリガー: リンク領域の `sign in`（`routerLink="/login"`）のクリック。
- 処理手順: ログイン画面へ遷移する。入力内容を破棄するかどうかの確認はしない。
- 状態変化: なし（画面が破棄される）。
- 遷移: `/login`。

### 5.3 API呼び出し一覧

| No. | 目的 | メソッド | パス | 要求パラメーター | 応答 | 成功時 | エラー時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 登録 | POST | `api/register` | 本文: `login`、`email`、`password`、`langKey`（現在の言語。`translateService.getCurrentLang()` の値、`null` なら `en`） | 201: 本文なし | `success` を `true` にし、フォームを隠して成功アラートを表示する | 応答に応じて「Login name already registered!」、「Email is already in use!」、「Registration failed!」のいずれかを表示する。フォームは残る |

補足:

- 呼び出し元は `Register.register()` の `RegisterService.save()`（`src/app/account/register/register.service.ts`）である。URL の起点は `serverApiUrl` で、中身はビルド時定数 `SERVER_API_URL` である（`src/app/config/endpoint.constants.ts`）。
- `langKey` について: アプリの起動時に、保存された言語がなければ言語は `en` になる（`src/app/shared/language/translation.provider.ts`）。選択できる言語は `LANGUAGES`（`src/app/config/language.constants.ts`）に `en` だけが定義されている。コードからは、このアプリケーションでは `langKey` は常に `en` になると読める。
- バックエンドの `@Valid` による制約は次のとおりである（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/vm/ManagedUserVM.java` と、その親クラスの `src/main/java/io/github/jhipster/sample/service/dto/AdminUserDTO.java`）。`password` は `@Size(min = 4, max = 100)`、`login` は `@NotBlank`、`@Pattern`、`@Size(min = 1, max = 50)`、`email` は `@Email`、`@Size(min = 5, max = 254)`、`langKey` は `@Size(min = 2, max = 10)` である。違反は 400 になる。エラーごとの表示は [登録_入力チェック一覧](./登録_入力チェック一覧.md) の 4 章に書く。
- 画面はエラーをレスポンス本文の `type`（`LOGIN_ALREADY_USED_TYPE`、`EMAIL_ALREADY_USED_TYPE`。`src/app/shared/jhipster/error.constants.ts`）で判別する。400 のレスポンスヘッダー `x-jhipstersampleapplicationapp-error` と `x-jhipstersampleapplicationapp-params` は、この画面では使わない。
- 要求ヘッダーは `authInterceptor` が `Authorization: Bearer <トークン>` を付ける（ストレージにトークンがあるとき）。
