## 2. 概要

- 本アプリケーションは JHipster のサンプルアプリケーションの Angular フロントエンドであり（`package.json` の `description`）、`bootstrapApplication` で起動する 1 個の Angular アプリケーションである。コードには JHipster の生成を示す接頭 `jhipster-needle-` のコメントが残っている（例: `src/app/admin/admin.routes.ts` の `jhipster-needle-add-admin-route`）。
- 画面はすべてスタンドアロンのコンポーネントで、ルートの単位で遅延読み込みする（5 章）。
- バックエンドの REST API を `HttpClient` で呼ぶ。URL は `${serverApiUrl}api/...` と `${serverApiUrl}management/...` の形である（7.5）。
- 認証は JWT の Bearer トークンである。トークンは Web Storage に置き、インターセプターが `Authorization` ヘッダーに付ける（7.2）。
- 状態はシグナル（`signal`、`computed`、`effect`）で持つ。一覧の取得は `httpResource`、単票の登録・更新・取得・削除は Observable である（6 章）。
- 全画面は `Main` のレイアウトの中に表示される。レイアウトはページリボン、名前付きアウトレット `navbar`、既定の `<router-outlet />`、フッターからなる（3.1）。
- 表示文言は ngx-translate で翻訳する。翻訳データは `src/i18n/en/` 配下に英語だけがある（8 章）。
- サービスは `@Service()` を付けたクラスで、依存は `inject()` 関数で受け取る。`@Injectable()` は `src/` 配下にない。

## 4. 起動と依存の注入

### 4.1 起動の順序

1. ブラウザーが `src/index.html` を読む。`<jhi-app>` の中にはローディング表示と、起動できないときの案内（`id="jhipster-error"`）がある。案内は `window.onload` の 4 秒後に表示される（`setTimeout(showError, 4000)`）。`<base href="/" />` がある。
2. `src/main.ts` が `import('./bootstrap')` で `src/bootstrap.ts` を動的に読み込む。読み込みに失敗したときは `console.error(err)` を出す。
3. `src/bootstrap.ts` が `bootstrapApplication(App, appConfig)` を呼ぶ。成功したときは `console.log('Application started')` を出す。
4. `appConfig` のプロバイダーが登録される（4.2）。`src/app/app.config.ts` の `import './config/dayjs'` により、dayjs のプラグイン（`customParseFormat`、`duration`、`relativeTime`）とロケール `en` が有効になる。
5. `provideTranslation()` の `provideAppInitializer` が翻訳の初期言語を確定する（8.4）。
6. `App` のコンストラクターが動く。英語のロケールデータを `registerLocaleData(locale)` で登録し、`iconLibrary.addIcons(...fontAwesomeIcons)` で 38 個のアイコンを登録し、`dpConfig.minDate` を 100 年前の 1 月 1 日にする。
7. `App` のテンプレートにより `Main` が生成される。`Main.ngOnInit()` は `accountService.identity().subscribe()` でアカウントを取得し（6.2）、`translateService.onLangChange` を購読する（8.4）。
8. `Main` のテンプレートの `<router-outlet name="navbar" />` に `Navbar` が、`<router-outlet />` に最初のルートの画面が表示される。`PageRibbon` のコンストラクターと `Navbar.ngOnInit()` は `ProfileService.getProfileInfo()` を呼ぶ（`GET management/info`）。

| 手順 | 主なコード | 根拠 |
| --- | --- | --- |
| 1 | ローディング表示、`#jhipster-error` | `src/index.html` |
| 2 | `import('./bootstrap')` | `src/main.ts` |
| 3 | `bootstrapApplication(App, appConfig)` | `src/bootstrap.ts` |
| 4 | `appConfig`、`import './config/dayjs'` | `src/app/app.config.ts`、`src/app/config/dayjs.ts` |
| 5 | `provideAppInitializer` | `src/app/shared/language/translation.provider.ts` |
| 6 | `registerLocaleData(locale)`、`iconLibrary.addIcons`、`dpConfig.minDate` | `src/app/app.ts`、`src/app/config/font-awesome-icons.ts` |
| 7 | `accountService.identity()`、`translateService.onLangChange` | `src/app/layouts/main/main.ts` |
| 8 | `<jhi-page-ribbon />`、`<router-outlet name="navbar" />` | `src/app/layouts/main/main.html`、`src/app/layouts/profiles/page-ribbon.ts`、`src/app/layouts/navbar/navbar.ts` |

### 4.3 依存の受け取り方

- クラス（サービス、コンポーネント、ディレクティブ、パイプ）は `inject()` 関数で依存を受け取る。`@Service()` は `src/` 配下（単体テストを除く）の 32 ファイルに 38 か所ある。`@Service()` を付けたクラスにコンストラクター引数による注入はなく、`inject()` は 168 か所にある（`src/` 配下の `*.ts`、単体テストを除く）。
- インターセプター、ルートガード、リゾルバーは関数であり、関数の中で `inject()` を呼ぶ（`src/app/core/interceptor/*.interceptor.ts`、`src/app/core/auth/user-route-access.service.ts`、`src/app/entities/**/route/*-routing-resolve.service.ts`）。
- テンプレート上の要素は `viewChild.required<ElementRef>('username')` の形で受け取る（`src/app/login/login.ts`、`src/app/account/register/register.ts` など）。
- パスエイリアスは `tsconfig.json` の `paths` による（3.3、9.2）。バレル（`index.ts`）は `export * from` でモデルとサービスをまとめて再エクスポートする（例: `src/app/core/auth/index.ts`）。

### 5.3 ルートガード

ガードは関数 `userRouteAccessService`（`CanActivateFn`）である（`src/app/core/auth/user-route-access.service.ts`）。詳細は [ルートガードと認可_画面設計書](../../共通/ルートガードと認可/ルートガードと認可_画面設計書.md) に書く。

1. `accountService.identity()` を呼び、アカウントを得る（6.2）。
2. アカウントがあるとき、ルートの `data.authorities` がないか空、または `accountService.hasAnyAuthority(authorities)` が `true` なら通す。
3. アカウントがあっても権限が足りないときは、開発モード（`isDevMode()`）なら `console.error(...)` を出し、`router.navigate(['accessdenied'])` で遷移して拒否する。
4. アカウントがないときは `stateStorageService.storeUrl(state.url)` で要求された URL を保存し、`router.navigate(['/login'])` で遷移して拒否する。保存した URL はログイン後に `AccountService.navigateToStoredUrl()` が使う。

### 5.4 リゾルバー

### 5.5 ナビゲーションエラーとエラー画面

- `withNavigationErrorHandler` は `NavigationError` を受け、`e.error.status` に応じて `router.navigate` を呼ぶ。403 は `/accessdenied`、404 は `/404`、401 は `/login`、それ以外は `/error` である（`src/app/app.config.ts`）。
- `/error`、`/accessdenied`、`/404` は同じコンポーネント `Error`（`src/app/layouts/error/error.ts`）を使う。`/accessdenied` と `/404` はルートの `data.errorMessage` に翻訳キーを持つ（`src/app/layouts/error/error.route.ts`）。
- `Error.ngOnInit()` は `route.data` を購読し、`errorMessage` があれば `translateService.get(this.errorKey)` で翻訳してシグナル `errorMessage` に入れる。テンプレートは見出し（翻訳キー `error.title`）と、`errorMessage()` があるときの危険アラートを表示する（`src/app/layouts/error/error.html`）。
- 未定義のパスは `path: '**'` のルートが `/404` へリダイレクトする。詳細は [エラー画面_画面設計書](../../共通/エラー画面/エラー画面_画面設計書.md) に書く。

### 5.6 ブラウザーのタイトル

- `AppPageTitleStrategy`（`TitleStrategy` の派生クラス、`@Service()`）は `updateTitle(routerState)` で `buildTitle(routerState)` の結果を得る。`undefined` なら翻訳キー `global.title` を使い、`translateService.get(pageTitle)` の結果を `title.setTitle(title)` で設定する（`src/app/app-page-title-strategy.ts`）。
- ルートの `title` は翻訳キーである（5.1）。
- 言語が変わったときは `Main` が `titleStrategy.updateTitle(this.router.routerState.snapshot)` を呼び直す（`src/app/layouts/main/main.ts`）。詳細は [画面タイトル_画面設計書](../../共通/画面タイトル/画面タイトル_画面設計書.md) に書く。

### 6.2 アカウント状態（`AccountService`）

`AccountService`（`src/app/core/auth/account.service.ts`）がアカウント状態の唯一の持ち主である。

| メンバー | 種類 | 内容 |
| --- | --- | --- |
| `userIdentity` | `signal`（`private`） | ログイン中のアカウント（`Account`）または `null` |
| `account` | 読み取り専用シグナル | `userIdentity.asReadonly()`。画面とディレクティブはこれを購読する |
| `accountCache$` | `Observable`（`private`） | `GET api/account` の結果のキャッシュ（`shareReplay()`） |
| `identity(force?)` | メソッド | キャッシュがないか `force` が `true` のとき `fetch()`（`GET api/account`）を呼ぶ。成功したら `authenticate(account)` を実行し、`account.langKey` があって保存された言語がなければ `translateService.use(account.langKey)` を実行し、`navigateToStoredUrl()` を呼ぶ。失敗は `catchError(() => of(null))` で `null` に変える |
| `authenticate(identity)` | メソッド | シグナルに値を設定する。`null` のときはキャッシュも消す |
| `hasAnyAuthority(authorities)` | メソッド | アカウントの `authorities` に引数の権限のどれかが含まれるかを返す |
| `isAuthenticated()` | メソッド | シグナルの値が `null` でないかを返す |
| `save(account)` | メソッド | `POST api/account` |
| `navigateToStoredUrl()` | メソッド（`private`） | 保存された URL があれば消してそこへ遷移する |

アカウント状態の流れは次のとおりである。

- 画面を開いたとき: `Main.ngOnInit()` の `identity()` が `GET api/account` を呼ぶ。トークンがあれば `authInterceptor` が付ける（7.2）。応答の `Account` がシグナルに入る。失敗すれば `null` が流れ、未ログインとして扱われる。
- ログイン: `Login.login()` が `LoginService.login(credentials)` を呼ぶ。`AuthServerProvider.login()` が `POST api/authenticate` でトークンを得て保存し（7.2）、続いて `accountService.identity(true)` がアカウントを再取得する。
- ログアウト: `Navbar.logout()` が `LoginService.logout()` を呼ぶ。`AuthServerProvider.logout()` がトークンを削除し、完了後に `accountService.authenticate(null)` がシグナルとキャッシュを消す。バックエンドは呼ばない。
- 設定の保存: `Settings.save()` は `accountService.save(account)` の成功時に `accountService.authenticate(account)` でシグナルを更新する。
- HTTP 401: `authExpiredInterceptor` がログアウトして `/login` へ遷移する（7.1）。

`account` シグナルを読んでいるのは、`Home`、`Navbar`、`Password`、`UserManagement`、`HasAnyAuthorityDirective` である（各ファイルの `inject(AccountService).account`）。詳細は [アカウント状態と認証_画面設計書](../../共通/アカウント状態と認証/アカウント状態と認証_画面設計書.md) に書く。

### 6.3 一覧の取得

エンティティの複数形のサービス（`BankAccountsService`、`LabelsService`、`OperationsService`、`UserManagementsService`、`AuthoritiesService`、`UsersService`）は同じ 3 部品を持つ（`src/app/entities/**/service/*.service.ts`）。

| 部品 | 種類 | 内容 |
| --- | --- | --- |
| `<entity>sParams` | `signal` | 一覧取得のクエリパラメーター。初期値は `undefined` |
| `<entity>sResource` | `httpResource` | `<entity>sParams()` が `undefined` ならリクエストしない。値があれば `{ url: this.resourceUrl, params }` で `GET` を送る |
| `<entity>s` | `computed` | `<entity>sResource.hasValue()` なら `value()`、そうでなければ空配列 |

一覧画面のデータの流れ（`src/app/entities/bank-account/list/bank-account.ts` を例にする）:

```
ルートの queryParamMap と data
  └ activatedRouteState（toSignal、初期値は snapshot）
      └ effect（untracked で包む。ルートの変化だけをトリガーにする）
          ├ fillComponentAttributeFromRoute()   sortState を設定
          └ load() → queryBackend()
              └ bankAccountService.bankAccountsParams.set({ eagerload: true, sort: [...] })
                  └ bankAccountsResource（httpResource）が GET api/bank-accounts を送る
                      └ bankAccounts（サービスの computed）
                          └ effect
                              └ 画面の bankAccounts シグナル（fillComponentAttributesFromResponseBody）
```

画面は `readonly isLoading = this.bankAccountService.bankAccountsResource.isLoading;` で読み込み中の状態を取る。並び替えは `SortDirective` がクエリパラメーター `sort` に反映し、上の流れで再取得する。

一覧画面は 3 つの形がある。

| 形 | 画面 | クエリパラメーター（`queryBackend()`） | 結果の持ち方 | レスポンスヘッダーの利用 | 根拠 |
| --- | --- | --- | --- | --- | --- |
| 全件取得 | `BankAccount`、`Label`、`Authority` | `sort`（`BankAccount` は `eagerload: true` も指定） | 取得ごとに置き換える。`refineData()` で `sortState` に従い画面内で並び替える | なし | `src/app/entities/bank-account/list/bank-account.ts`、`src/app/entities/label/list/label.ts`、`src/app/entities/admin/authority/list/authority.ts` |
| 無限スクロール | `Operation` | `size`（`ITEMS_PER_PAGE`）、`eagerload: true`。続きのページは `links().next` の内容、初回だけ `sort` | 既存の一覧にない `id` の項目だけを追記する | `link` ヘッダーを `ParseLinks.parseAll()` で解析し、シグナル `links` に保持する。`hasMorePage`、`isFirstFetch` は `computed` | `src/app/entities/operation/list/operation.ts` |
| ページング | `UserManagement` | `page`（0 始まり）、`size`、`sort` | 取得ごとに置き換える | `X-Total-Count` ヘッダー（`TOTAL_COUNT_RESPONSE_HEADER`）をシグナル `totalItems` に保持する | `src/app/entities/admin/user-management/list/user-management.ts` |

`Operation` のテンプレートは `<tbody infinite-scroll (scrolled)="loadNextPage()" [infiniteScrollDisabled]="!hasMorePage()" [infiniteScrollDistance]="0">` であり、`UserManagement` のテンプレートは `<jhi-item-count>` と `<ngb-pagination (pageChange)="navigateToPage($event)">` を持つ（`src/app/entities/operation/list/operation.html`、`src/app/entities/admin/user-management/list/user-management.html`）。

### 6.4 登録・編集

登録・編集画面のデータの流れ（`src/app/entities/bank-account/update/bank-account-update.ts` を例にする）:

1. フィールド `editForm` の初期化で `bankAccountFormService.createBankAccountFormGroup()` を引数なしで呼び、空のフォームを作る。
2. `ngOnInit()` が `activatedRoute.data` を購読する。リゾルバーの結果 `bankAccount` があれば `updateForm(bankAccount)` を呼ぶ。`updateForm` は `bankAccountFormService.resetForm(this.editForm, bankAccount)` でフォームに値を入れ、`usersSharedCollection` に現在の関連の値を補う。
3. `loadRelationshipsOptions()` が `userService.query()`（`GET api/users`）で選択肢を取り、`addUserToCollectionIfMissing()` で現在の値を補ってシグナル `usersSharedCollection` に入れる。
4. 保存ボタン（`(ngSubmit)="save()"`、`[disabled]="editForm.invalid || isSaving()"`）で `save()` が動く。`isSaving` を `true` にし、`bankAccountFormService.getBankAccount(this.editForm)` でモデルを得る。
5. `bankAccount.id === null` なら `bankAccountService.create()`（`POST api/bank-accounts`）、そうでなければ `bankAccountService.update()`（`PUT api/bank-accounts/{id}`）を呼ぶ。
6. `subscribeToSaveResponse` は、成功 (`next`) なら `onSaveSuccess()` で `previousState()`（`globalThis.history.back()`）により戻る。`finalize` で `isSaving` を `false` に戻す。失敗 (`error`) の `onSaveError()` は何もしない（表示は `<jhi-alert-error />` が担う、7.3）。

状態は `isSaving`（`signal`）、`bankAccount`（クラスのフィールド）、`usersSharedCollection`（`signal`）、`editForm`（`FormGroup`）である。関連を 2 つ持つ `OperationUpdate` は `bankAccountsSharedCollection` と `labelsSharedCollection` を持つ（`src/app/entities/operation/update/operation-update.ts`）。`AuthorityUpdate` は `create()` だけを呼ぶ（`src/app/entities/admin/authority/update/authority-update.ts`）。

### 6.5 通知（`AlertService` と `EventManager`）

- `AlertService`（`src/app/core/util/alert.service.ts`）はシグナル `alertsSignal`（`AlertModel[]`）を持ち、`alerts` はその読み取り専用版である。`addAlert()` はアラートに連番の `id` を付け、`translationKey` があれば `translateService.instant()` で翻訳し、`DomSanitizer.sanitize(SecurityContext.HTML, ...)` を通し、既定値（`timeout` は 5000、`toast` は `false`、`position` は `'top right'`）を補う。`timeout` が正なら `setTimeout()` で閉じる。
- 成功アラートは `notificationInterceptor` がサービスのシグナルに足し、`Alert`（`jhi-alert`）が表示する（7.4）。`Alert.ngOnDestroy()` は `alertService.clear()` を呼ぶ。
- エラーアラートは `AlertError`（`jhi-alert-error`）が自分のシグナル `alerts` に足して表示する。`addAlert()` の第 2 引数に自分のシグナルを渡すことで、表示は `<jhi-alert-error />` を置いた画面単位に閉じる（7.3）。
- `EventManager`（`src/app/core/util/event-manager.service.ts`）は 1 本の Observable を共有する配信手段である。`broadcast()` が `observer.next()` を呼び、`subscribe(eventNames, callback)` はイベント名で絞って購読する。

## 7. HTTP共通処理

### 7.1 インターセプターの連鎖

`provideHttpClient(withInterceptors([authInterceptor, authExpiredInterceptor, errorHandlerInterceptor, notificationInterceptor]))` の配列の順に登録されている（`src/app/app.config.ts`）。リクエストは配列の順に、レスポンスは逆順に各インターセプターを通る。これは Angular の `withInterceptors` の仕様であり、本リポジトリのコードではない。

| 順 | インターセプター | リクエスト側 | レスポンス・エラー側 | 根拠 |
| --- | --- | --- | --- | --- |
| 1 | `authInterceptor` | 対象のリクエストに `Authorization: Bearer <トークン>` を付ける（7.2） | 何もしない | `src/app/core/interceptor/auth.interceptor.ts` |
| 2 | `authExpiredInterceptor` | 何もしない | 401 で、URL に `api/account` を含まないとき、現在の URL を保存し、ログアウトして `/login` へ遷移する | `src/app/core/interceptor/auth-expired.interceptor.ts` |
| 3 | `errorHandlerInterceptor` | 何もしない | エラーをイベント `jhipsterSampleApplicationApp.httpError` として配信する（7.3） | `src/app/core/interceptor/error-handler.interceptor.ts` |
| 4 | `notificationInterceptor` | 何もしない | 成功応答のヘッダーから成功アラートを作る（7.4） | `src/app/core/interceptor/notification.interceptor.ts` |

`authExpiredInterceptor` の 401 の処理は、`stateStorageService.storeUrl(router.routerState.snapshot.url)`、`loginService.logout()`、`router.navigate(['/login'])` である。`api/account` の 401 は、ログインしていない状態でのアカウント取得の失敗に当たるため、対象外である。詳細は [HTTP共通処理_画面設計書](../../共通/HTTP共通処理/HTTP共通処理_画面設計書.md) に書く。

### 7.2 認証トークン

- トークンの保存場所は `StateStorageService`（`src/app/core/auth/state-storage.service.ts`）である。キーは `AUTHENTICATION_TOKEN_KEY`（`'jhi-authenticationToken'`、`src/app/shared/jhipster/constants.ts`）で、値は `JSON.stringify()` した文字列である。
- `storeAuthenticationToken(token, rememberMe)` は、両方のストレージからトークンを消してから、`rememberMe` が `true` なら `localStorage`、`false` なら `sessionStorage` に書く。
- `getAuthenticationToken()` は `localStorage` を先に調べ、なければ `sessionStorage` を調べる。
- `authInterceptor` は、URL がないか、`http` で始まり `serverApiUrl` から始まらない URL（外部のオリジン）のときは何もしない。それ以外でトークンがあれば `req.clone({ setHeaders: { Authorization: 'Bearer <トークン>' } })` を実行する。
- トークンは `AuthServerProvider.login()` が `POST api/authenticate` の応答 `id_token` から得て保存する（`src/app/core/auth/auth-jwt.service.ts`）。
- バックエンドは `/api/**` に認証を要求する。認証なしでよいのは `POST` と `GET` の `/api/authenticate`、`/api/register`、`/api/activate`、`/api/account/reset-password/init`、`/api/account/reset-password/finish` と、`/management/health`、`/management/info`、`/management/prometheus` である。`/api/admin/**`、`/v3/api-docs/**`、`/management/**` は `ROLE_ADMIN` を要求する。開発のプロファイルのときは `/h2-console/**` も認証なしである（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）。

### 7.3 エラーの処理と表示

- `errorHandlerInterceptor` は、401 であって `err.message` が空、または URL に `api/account` を含む場合を除き、`EventManager.broadcast(new EventWithContent('jhipsterSampleApplicationApp.httpError', err))` を実行する。条件に当てはまる 401 は配信しない。
- `AlertError`（`src/app/shared/alert/alert-error.ts`）はコンストラクターでこのイベントを購読し、`handleHttpError()` でステータスに応じてアラートを足す。`ngOnDestroy()` で購読を解く。

| ステータス | 表示 | 根拠 |
| --- | --- | --- |
| 0（サーバーに到達できない） | 翻訳キー `error.server.not.reachable` | `src/app/shared/alert/alert-error.ts`（`handleHttpError()`）、`src/i18n/en/global.json` |
| 400 | レスポンスヘッダーの `x-jhipstersampleapplicationapp-error` と `x-jhipstersampleapplicationapp-params`、または本文の `fieldErrors`、`message`、`detail`、`params` から作ったアラート | 同上（`handleBadRequest()`、`handleFieldsError()`）、`src/app/shared/jhipster/headers.ts` |
| 404 | 翻訳キー `error.url.not.found` | 同上、`src/i18n/en/global.json` |
| 上記以外 | 本文の `message`、`detail`、`params` から作ったアラート | 同上（`handleDefaultError()`） |

- `handleFieldsError()` は `fieldErrors` の 1 件ごとに、項目名を `jhipsterSampleApplicationApp.<objectName>.<field>` で翻訳し、翻訳キー `error.<message>` のアラートに埋め込む。添え字（`[14]` など）は `[]` に置き換える。`Min`、`Max`、`DecimalMin`、`DecimalMax` のメッセージは `Size` に置き換える。
- 画面側の `error` コールバックは、ログインの `authenticationError` のように結果のシグナルを変えるものが中心である（6.6）。登録・編集画面の `onSaveError()` は空である。
- `<jhi-alert-error />` は 22 のテンプレートに置かれている（エンティティ 5 種の一覧・詳細・登録・編集・削除ダイアログの 20 と、設定、パスワード再設定依頼）。詳細は [アラート_画面設計書](../../共通/アラート/アラート_画面設計書.md) に書く。

### 7.4 成功通知

- バックエンドは登録・更新・削除の成功時にヘッダー `x-jhipstersampleapplicationapp-alert`（翻訳キー）と `x-jhipstersampleapplicationapp-params`（埋め込む値）を付けて返す（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/BankAccountResource.java` などの `HeaderUtil.createEntityCreationAlert()` などの呼び出し）。
- `notificationInterceptor` は `HttpResponse` を受け取ったとき、ヘッダーを `getMessageFromHeaders()` で読む（`src/app/shared/jhipster/headers.ts`）。翻訳キーと判定できれば `alertService.addAlert({ type: 'success', translationKey, translationParams: { param } })`、そうでなければ `alertService.addAlert({ type: 'success', message })` を実行する。
- 成功アラートは `AlertService` のシグナルに入るため、遷移先の画面の `<jhi-alert />` に表示される。`<jhi-alert />` はエンティティ 5 種の一覧と詳細の 10 テンプレートにある。

- 翻訳データは `src/i18n/en/` 配下の 19 ファイルである。`activate.json`、`adminAuthority.json`、`bankAccount.json`、`configuration.json`、`error.json`、`global.json`、`health.json`、`home.json`、`label.json`、`login.json`、`logs.json`、`metrics.json`、`operation.json`、`password.json`、`register.json`、`reset.json`、`sessions.json`、`settings.json`、`user-management.json`。
- エンティティの文言は `jhipsterSampleApplicationApp.<entity>.*`、画面固有の文言は `<画面名>.*`、共通の文言は `global.*` と `entity.*` である。最上位のキー `error` は `error.json` と `global.json` の両方にあり、マージされて 1 つの名前空間になる。
- `sessions.json` に対応する画面は `src/app/` にはない。

### 8.2 翻訳の読み込み

- `build-plugins/i18n-esbuild.ts` の `prepareLanguage()` は、言語ディレクトリ内の `*.json` を `deepmerge` で 1 つのオブジェクトに結合する。`i18n/<言語>.json` という仮想モジュールとして解決させるのは同じプラグインである（9.3）。
- `src/i18n/index.ts` の `loadLocale(locale)` は、Angular のロケールデータ（`@angular/common/locales/en`）を動的に読み込み、`i18n/<言語>.json` を返す。
- `translatePartialLoader()`（`src/app/config/translation.config.ts`）は `getTranslation(lang)` で `from(loadLocale(lang))` を返す `TranslateLoader` である。
- 未定義のキーは `MissingTranslationHandlerImpl` が `translation-not-found[<キー>]` に置き換える（`translationNotFoundMessage`）。

### 8.3 テンプレートでの翻訳

| 手段 | 使い方 | 根拠 |
| --- | --- | --- |
| `jhiTranslate` ディレクティブ | 要素の内容を翻訳キーで置き換える。`jhiTranslate`（必須の `input`）と `translateValues` を持ち、結果を要素の `innerHTML` に書く。`onLangChange` と `onTranslationChange` を購読して再描画する | `src/app/shared/language/translate.directive.ts` |
| `translate` パイプ（ngx-translate の `TranslatePipe`） | 属性値の翻訳（例: `placeholder="{{ 'global.form.username.placeholder' \| translate }}"`） | `src/app/login/login.html`、`src/app/account/register/register.html` など |
| `findLanguageFromKey` パイプ | 言語コードを言語名にする（`en` は `English`） | `src/app/shared/language/find-language-from-key.pipe.ts`、`src/app/layouts/navbar/navbar.html` |
| `TranslateService` の `get()`、`instant()` | コンポーネントやサービスからの翻訳 | `src/app/app-page-title-strategy.ts`（`get()`）、`src/app/core/util/alert.service.ts`（`instant()`） |

### 8.4 言語の切り替え

- アプリの初期化時、`provideAppInitializer` が `translateService.setFallbackLang('en')` を呼び、`translateService.use(stateStorageService.getLocale() ?? 'en')` で言語を確定する（`src/app/shared/language/translation.provider.ts`）。
- ログイン後（アカウント取得後）、`account.langKey` があってセッションに言語の保存がなければ、`account.langKey` に切り替わる（`src/app/core/auth/account.service.ts` の `identity()`）。
- ナビゲーションバーの言語メニューは `languages.length > 1` のときだけ表示される。現在は `LANGUAGES` が 1 つであるため表示されない（`src/app/layouts/navbar/navbar.html`）。`Navbar.changeLanguage()` は `stateStorageService.storeLocale(languageKey)` と `translateService.use(languageKey)` を呼ぶ。
- 設定画面の保存後、`account.langKey` が現在の言語と違えば `translateService.use(account.langKey)` を呼ぶ（`src/app/account/settings/settings.ts`）。
- 言語が変わると `Main` はブラウザーのタイトルを更新し、`dayjs.locale(lang)` を設定し、`<html>` の `lang` 属性を書き換える（`src/app/layouts/main/main.ts`）。

言語の保存キーは `locale`（`sessionStorage`）である（`src/app/core/auth/state-storage.service.ts`）。詳細は [国際化_画面設計書](../../共通/国際化/国際化_画面設計書.md) に書く。

## 10. 画面共通の作り

### 10.1 画面を構成する部品の並び

エンティティの画面は、ルート、リゾルバー、コンポーネント、フォームサービス、サービス、モデルが次の並びでつながる。

```
ルート定義（<entity>.routes.ts）
  ├ canActivate: [userRouteAccessService]             ガード（5.3）
  ├ resolve: { <entity>: <Entity>Resolve }            リゾルバー（5.4）
  │     └ <Entity>Service.find(<識別子>)              GET api/<entity>s/{識別子}
  └ loadComponent                                     画面（遅延読み込み）
        ├ 一覧画面      <Entity>Service の …Params → httpResource → …（computed）→ 画面のシグナル
        ├ 詳細画面      input でリゾルバーの結果を受け、表示する
        └ 登録・編集画面  ActivatedRoute.data → フォームサービス（FormGroup） → <Entity>Service.create() / update()
```

| 部品 | 役割 | 銀行口座の例 |
| --- | --- | --- |
| モデル（`*.model.ts`） | API でやり取りするデータの型（`I…`）と、登録時に主キーが `null` になる型（`New…`） | `src/app/entities/bank-account/bank-account.model.ts` |
| サービス（`*.service.ts`） | API の呼び出し。一覧は `httpResource`、単票は `create()`、`update()`、`partialUpdate()`、`find()`、`query()`、`delete()` の Observable。識別子の比較 (`compare` で始まる名前のメソッド) と選択肢の補完 (`add` で始まり `ToCollectionIfMissing` で終わる名前のメソッド) も持つ。`AuthorityService` には `update()` と `partialUpdate()` がなく、`UserService` には `create()`、`update()`、`partialUpdate()`、`delete()` がない | `src/app/entities/bank-account/service/bank-account.service.ts`、`src/app/entities/admin/authority/service/authority.service.ts`、`src/app/entities/user/service/user.service.ts` |
| リゾルバー（`route/*-routing-resolve.service.ts`） | 画面を開く前に 1 件を取得する | `src/app/entities/bank-account/route/bank-account-routing-resolve.service.ts` |
| フォームサービス（`update/*-form.service.ts`） | `FormGroup` の生成 (`create…FormGroup()`)、フォーム値からモデルへの変換 (`get…()`)、モデルからフォームへの反映 (`resetForm()`) | `src/app/entities/bank-account/update/bank-account-form.service.ts` |
| 画面コンポーネントとテンプレート | 一覧、詳細、登録・編集の 3 種類の画面と、削除ダイアログ | `src/app/entities/bank-account/list/`、`detail/`、`update/`、`delete/` |
| ルート定義（`*.routes.ts`） | 遅延読み込み、`resolve`、`canActivate`、`data` | `src/app/entities/bank-account/bank-account.routes.ts` |

モデルの内容は [DTO設計書](../../../03_IF設計/01_DTO設計書/README.md) に、API の要求・応答は [電文レイアウト](../../../03_IF設計/02_電文レイアウト/README.md) に書く。

### 10.2 画面の種類ごとの形

| 種類 | 作り | 根拠（例） |
| --- | --- | --- |
| 一覧画面 | ルートのクエリパラメーターをシグナルに入れ、サービスの `…Params` を経て `httpResource` で取得する（6.3）。並び替えは `jhiSort` と `jhiSortBy`、状態は `SortService` がクエリパラメーター `sort` と相互変換する | `src/app/entities/bank-account/list/bank-account.ts`、`src/app/shared/sort/sort.service.ts` |
| 詳細画面 | リゾルバーの結果を `input` で受け、表示だけを行う。API は呼ばない | `src/app/entities/bank-account/detail/bank-account-detail.ts` |
| 登録・編集画面 | リゾルバーの結果を `activatedRoute.data` で受け、フォームサービスで `FormGroup` に反映する。主キーが `null` なら登録、そうでなければ更新である（6.4） | `src/app/entities/bank-account/update/bank-account-update.ts` |
| 削除ダイアログ | ルートを持たないモーダル。一覧画面が `NgbModal` で開き、`componentInstance` で対象を渡す。削除が成功したら `activeModal.close(ITEM_DELETED_EVENT)` で閉じ、一覧画面が再取得する | `src/app/entities/bank-account/delete/bank-account-delete-dialog.ts`、`src/app/entities/bank-account/list/bank-account.ts` |
| アカウント系の画面 | 画面の中で `FormGroup` を作り、専用のサービス 1 つで API を呼ぶ。結果はシグナルで持つ | `src/app/account/register/register.ts`、`src/app/account/register/register.service.ts` |
| 管理画面 | 専用のサービスで `management/...` を呼び、結果をシグナルで持つ。絞り込みと並び替えは `computed` で行う | `src/app/admin/logs/logs.ts`、`src/app/admin/logs/logs.service.ts` |

### 10.3 テンプレートの共通の書き方

- 制御構文は `@if`、`@for`、`@let`、`@defer` である。`*ngIf`、`*ngFor`、`ngClass`、`[(ngModel)]` は `src/` 配下のテンプレートにない（`src/` 配下の `*.html`）。
- 文言は `jhiTranslate="<翻訳キー>"` で置き、要素の内容には英語の既定文言を残す。属性値は `translate` パイプを使う（8.3）。
- 操作の対象には `data-cy="<名前>"` を付ける（`src/` 配下の 32 のテンプレートに 124 か所）。
- アイコンは `<fa-icon icon="<名前>" />` である。使える名前は `fontAwesomeIcons` に登録した 38 個である（4.1）。
- 戻る操作は `previousState()` が `globalThis.history.back()` を呼ぶ（エンティティ 5 種の詳細画面と登録・編集画面の 10 クラスにある）。
- 保存ボタンは `[disabled]="editForm.invalid || isSaving()"` で制御する（エンティティ 5 種の登録・編集画面）。
