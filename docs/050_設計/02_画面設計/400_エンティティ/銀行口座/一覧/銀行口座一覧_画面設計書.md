## 2. 機能概要

- 銀行口座（`IBankAccount`）の一覧をテーブル形式で表示する。
- 一覧は `GET api/bank-accounts` で全件を取得する。ページングと無限スクロールはない。
- 取得した一覧はサービスの `bankAccountsResource`（`httpResource`）が保持し、画面はその値をシグナル `bankAccounts` に写す。
- 見出し行の ID、Name、Balance、User の 4 列をクリックして並び替えられる。並び替えの状態はクエリパラメーター `sort` に反映され、画面を再読み込みしても同じ並び順になる。
- 並び替えのたびにバックエンドへ再取得に行く。バックエンドは `sort` を使わないため、並び替えは画面側（`refineData()`）で行う。
- クエリパラメーター `eagerload=true` を付けて取得し、バックエンドに関連するユーザー（`user`）を一緒に読み込ませる。
- 「Refresh list」ボタンで一覧を再取得する。
- 「Create a new Bank Account」ボタンで登録画面へ遷移する。
- 各行に詳細表示、編集、削除の操作がある。削除は確認ダイアログを開き、削除が完了したら一覧を再取得する。
- 件数が 0 件のときはテーブルの代わりに「No Bank Accounts found」の警告を表示する。
- HTTP エラーは `<jhi-alert-error />` に、登録・更新・削除の成功通知は `<jhi-alert />` に表示する。

## 3. 画面レイアウト

画面は `Main` の `<router-outlet />` の中、`<div class="card jh-card">` の内側に表示される（`src/app/layouts/main/main.html`）。テンプレートのルートは `<div>` 1 つで、その中を上から順に次の領域が占める。

```
見出し領域（<h2 id="page-heading" data-cy="BankAccountHeading">）
    Bank Accounts
    [Refresh list]
    [Create a new Bank Account]
アラート領域
    <jhi-alert-error />   … エラー
    <jhi-alert />         … 成功通知
検索結果なし領域（#no-result）      … bankAccounts().length === 0 のとき

    ヘッダー行: ID | Name | Balance | User | （操作）
```

### 5.2 イベント詳細

#### 5.2.1 画面初期化

- トリガー: コンポーネントが生成された後の最初の変更検知で、`constructor` 内の 2 つの `effect` が実行される。以後はルートのクエリパラメーター（`sort`）が変わるたびに、2 つ目の `effect` が再実行される。
- 処理手順:
  1. `activatedRouteState`（`queryParamMap` と `data` を `toSignal` にしたもの）の初期値は `activatedRoute.snapshot` の値である。
  2. 2 つ目の `effect` が `untracked()` の中で `fillComponentAttributeFromRoute(queryParamMap, data)` を呼ぶ。`sortState` に `sortService.parseSortParam(params.get(SORT) ?? data[DEFAULT_SORT_DATA])` を設定する。クエリパラメーター `sort` がなければ、ルートの `data.defaultSort`（`id,asc`）を使う。
  3. 続けて `load()` を呼ぶ。`load()` は `queryBackend()` を呼ぶ。`queryBackend()` は `{ eagerload: true, sort: this.sortService.buildSortParam(this.sortState()) }` を `queryObject` として作り、`this.bankAccountService.bankAccountsParams.set(queryObject)` を実行する。
  4. サービス `BankAccountsService` の `bankAccountsResource`（`httpResource<IBankAccount[]>`）は `bankAccountsParams()` を見てリクエストを組み立てる。値が `undefined` ならリクエストしない。値があれば `{ url: this.resourceUrl, params }` として `GET api/bank-accounts` を送る。
  5. 応答が届くと `bankAccountsResource` の値が変わり、`computed` である `bankAccounts`（サービス）が変わる。
  6. 1 つ目の `effect` が `this.bankAccounts.set(this.fillComponentAttributesFromResponseBody([...this.bankAccountService.bankAccounts()]))` を実行する。`fillComponentAttributesFromResponseBody` は `refineData` を呼び、`sortState` の `predicate` と `order` で一覧を並び替えて、画面の `bankAccounts` シグナルに入れる。
- 状態変化: `sortState`、`bankAccountsParams`（サービス）、`isLoading`（`bankAccountsResource.isLoading`）、`bankAccounts`（サービスと画面）。
- 遷移: なし。

#### 5.2.2 Refresh list ボタンクリック

- トリガー: `(click)="load()"`。`isLoading()` が `true` の間はボタンが無効である。
- 処理手順: `load()` が `queryBackend()` を呼び、`bankAccountsParams` に新しいオブジェクトを設定する。以降は 5.2.1 の手順 4 から 6 と同じである。
- 状態変化: `bankAccountsParams`、`isLoading`、`bankAccounts`（`sortState` は変わらない）。
- 遷移: なし。

#### 5.2.3 並び替え（見出し行のクリック）

- トリガー: `jhiSortBy` を持つ `<th>` のクリック。`SortByDirective` はホスト要素の `(click)` で `onClick()` を呼ぶ。
- 処理手順:
  1. `SortByDirective.onClick()` が親の `SortDirective` の `this.sort.sort(this.jhiSortBy())` を呼ぶ。
  2. `SortDirective.sort(field)` は、今の `predicate` と同じ列なら `order` を `asc` と `desc` で反転させ、別の列なら `asc` にする。`sortState` を更新し、`sortChange` に新しい状態を出す。
  3. テンプレートの `(sortChange)="navigateToWithComponentValues($event)"` が `handleNavigation(sortState)` を呼ぶ。
  4. `handleNavigation` は `{ sort: this.sortService.buildSortParam(sortState) }` を `queryParamsObj` として作り、`this.router.navigate(['./'], { relativeTo: this.activatedRoute, queryParams: queryParamsObj })` を実行する。URL は `/bank-account?sort=<列>,<順>` になる（例: `/bank-account?sort=name,desc`）。
  5. クエリパラメーターが変わると `activatedRouteState` が変わり、5.2.1 と同じ流れで、並び替え状態の設定、再取得、画面側の並び替えが行われる。
  6. `SortByDirective` の `effect` は、`<th>` の中の `<fa-icon>` のアイコンを `sortState` に応じて切り替える（対象の列でなければ `faSort`、`asc` なら `faSortUp`、`desc` なら `faSortDown`）。
- 並び替えの実体: `refineData()` は、`sortState` に `predicate` と `order` の両方があるとき `data.sort(this.sortService.startSort({ predicate, order }))` で並び替える。`startSort` の比較には `new Intl.Collator(undefined, { numeric: true, sensitivity: 'base' })` を使い、`desc` のときは比較結果の符号を反転する。
- バックエンドとの関係: `queryBackend()` は `sort` をクエリパラメーターで送るが、バックエンドの `BankAccountResource.getAllBankAccounts()` には `sort` を受け取る引数がなく、呼び出すリポジトリーメソッドのクエリーにも並び順を指定する句がない。並び順は画面側の `refineData()` だけで決まる。
- User 列の注意: `startSort` は項目の `a[predicate]` を直接比較する。`user.login` というキーのプロパティーは項目にないため、比較結果はすべて等しくなる。コードからは、User 列で並び替えても表示順は変わらず、アイコンだけが変わると読める。
- 状態変化: `sortState`、URL のクエリパラメーター `sort`、5.2.1 と同じシグナル群。
- 遷移: 画面遷移はない（同じルート `/bank-account` のクエリパラメーターだけが変わる）。

#### 5.2.4 Delete ボタンクリック（削除ダイアログを開く）

- トリガー: `(click)="delete(bankAccount)"`。
- 処理手順:
  1. `this.modalService.open(BankAccountDeleteDialog, { size: 'lg', backdrop: 'static' })` で削除ダイアログを開く。`backdrop: 'static'` は、背景をクリックしてもダイアログを閉じない ng-bootstrap の指定である。
  2. `modalRef.componentInstance.bankAccount = bankAccount` で、削除対象をダイアログに渡す。
  3. `modalRef.closed` を購読する。`closed` はダイアログが `close()` で閉じられたときに流れる Observable である（`dismiss()` で閉じられたときは流れない）。
  4. 理由が `ITEM_DELETED_EVENT`（`'deleted'`）のときだけ `load()` を呼び、一覧を再取得する。
- 状態変化: ダイアログが開く。削除が確定した場合は、5.2.1 の手順 4 から 6 と同じシグナル群が変わる。
- 遷移: なし。ダイアログの中の処理（`DELETE api/bank-accounts/{id}`）は [銀行口座削除_画面設計書](../削除/銀行口座削除_画面設計書.md) に書く。

#### 5.2.5 リンクによる遷移

- トリガー: Create a new Bank Account ボタン、ID リンク、View、Edit のクリック。
- 処理手順: `[routerLink]` に従って遷移する。遷移先のルートには `canActivate: [userRouteAccessService]` がある。
- 遷移先: `/bank-account/new`、`/bank-account/:id/view`、`/bank-account/:id/edit`。
- 状態変化: この画面は破棄される。破棄のとき `<jhi-alert />`（`Alert`）の `ngOnDestroy()` が `alertService.clear()` を呼ぶ。

### 5.3 API呼び出し一覧

| No. | 目的 | メソッド | パス | 要求パラメーター | 応答 | 成功時 | エラー時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 一覧の取得 | GET | `api/bank-accounts` | クエリパラメーター: `eagerload`（`true` 固定）、`sort`（`<列>,<asc または desc>`。例: `id,asc`） | 200: `IBankAccount` の配列（`id`、`name`、`balance`、`user`） | `bankAccountsResource` が値を持ち、サービスの `bankAccounts` を経て画面の `bankAccounts` に入る | サービスの `bankAccounts` は空配列になる。エラーは `<jhi-alert-error />` に表示される |

補足:

- 呼び出し元は `BankAccountsService.bankAccountsResource`（`src/app/entities/bank-account/service/bank-account.service.ts`）である。URL は `resourceUrl`（`${serverApiUrl}api/bank-accounts`）で、`serverApiUrl` はビルド時定数 `SERVER_API_URL` である（`src/app/config/endpoint.constants.ts`）。
- `BankAccountService.query(req?)` も同じ URL を `HttpClient` の `get` で呼ぶが、この画面は使わない。本体で `BankAccountService` の `query()` を呼んでいるのは取引の登録・編集画面である（`src/app/entities/operation/update/operation-update.ts` の `loadRelationshipsOptions()`）。
- `eagerload` の効果（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/BankAccountResource.java`、`getAllBankAccounts(eagerload)`）: `true` のときは `bankAccountRepository.findAllWithEagerRelationships()` を呼ぶ。これは `left join fetch bankAccount.user` のクエリーで、銀行口座と一緒にユーザーを読み込む。`false` のときは `findAll()` を呼ぶ。引数の既定値は `true` である。
- バックエンドは DTO を使わず、エンティティのクラス `BankAccount`（バックエンドの `src/main/java/io/github/jhipster/sample/domain/BankAccount.java`。画面コンポーネントの `BankAccount` とは別のものである）をそのまま JSON で返す。フロントエンドの `IBankAccount` は `id`、`name`、`balance`、`user` を定義し、この画面はその 4 つだけを使う。
- 要求ヘッダーは `authInterceptor` が `Authorization: Bearer <トークン>` を付ける（トークンがあるとき）。バックエンドは `/api/**` に認証を要求する（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）。
- エラー時の共通の動きは次のとおりである。
  - 401 のときは `authExpiredInterceptor` が現在の URL を `StateStorageService.storeUrl()` で保存し、ログアウトして `/login` へ遷移する。
  - この画面の API に対する HTTP エラーは `errorHandlerInterceptor` がイベント `jhipsterSampleApplicationApp.httpError` として配信する（配信しないのは 401 で、かつ `message` が空か URL に `api/account` を含む場合だけである）。`AlertError` はステータスに応じた文言を `<jhi-alert-error />` に表示する（404 は `error.url.not.found`、サーバーに到達できないときは `error.server.not.reachable`、400 はレスポンスヘッダーや本文の内容を使う）。
