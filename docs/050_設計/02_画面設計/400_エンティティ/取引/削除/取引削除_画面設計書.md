## 2. 機能概要

- 取引を削除してよいか確認するモーダルダイアログである。ルートは持たず、取引一覧の Delete ボタンで開く。
- 削除の対象はプロパティー `operation` で受け取る。取引一覧が `modalRef.componentInstance.operation` に設定する。
- 本文に「Are you sure you want to delete Operation {{ id }}?」と対象の ID を表示する。
- Cancel でダイアログを閉じる。削除はしない。
- Delete で `DELETE api/operations/{id}` を送る。成功したらダイアログを理由 `ITEM_DELETED_EVENT` で閉じ、取引一覧が再取得する。
- 削除に失敗したらダイアログは開いたままで、エラーを `<jhi-alert-error />` に表示する。
- 入力項目はない。この画面に `入力チェック一覧` はない。

## 3. 画面レイアウト

ダイアログの中身は `<form name="deleteForm" (ngSubmit)="confirmDelete(operation.id)">` で、`@if (operation)` が真のときに表示する。フォームの中を上から順に次の領域が占める。

```
ダイアログ見出し領域（<div class="modal-header">）
    Confirm delete operation
ダイアログ本文領域（<div class="modal-body">）
    <jhi-alert-error />   … エラー
    Are you sure you want to delete Operation {{ id }}?
ダイアログボタン領域（<div class="modal-footer">）
    [Cancel] [Delete]
```

| 領域 | テンプレート上の要素 | 表示条件 | 4 章の対応 |
| --- | --- | --- | --- |
| ダイアログ見出し領域 | `<div class="modal-header">` | `operation` が設定されているとき | `### ダイアログ見出し領域` |
| ダイアログ本文領域 | `<div class="modal-body">`（`<jhi-alert-error />` と確認メッセージ） | 同上 | `### ダイアログ本文領域` |
| ダイアログボタン領域 | `<div class="modal-footer">`（Cancel ボタン、Delete ボタン） | 同上 | `### ダイアログボタン領域` |

## 5. イベント処理

### 5.1 イベント一覧

| No. | イベント発生源 | イベント | 遷移先 | イベント物理名 |
| --- | --- | --- | --- | --- |
| 1 | 取引一覧の Delete ボタン | クリック | なし（ダイアログを開く） | `delete(operation)`（取引一覧のメソッド） |
| 2 | Cancel ボタン | クリック | なし（ダイアログを閉じる） | `cancel()` |
| 3 | Delete ボタン | クリック（フォームの送信） | なし（削除に成功したらダイアログを閉じる） | `(ngSubmit)="confirmDelete(operation.id)"` |

### 5.2 イベント詳細

#### 5.2.1 ダイアログを開く

- トリガー: 取引一覧の Delete ボタン（`(click)="delete(operation)"`）。
- 処理手順:
  1. 取引一覧の `delete(operation)` が `this.modalService.open(OperationDeleteDialog, { size: 'lg', backdrop: 'static' })` を呼ぶ。`backdrop: 'static'` は、背景をクリックしてもダイアログを閉じない ng-bootstrap の指定である。
  2. `modalRef.componentInstance.operation = operation` で、削除の対象をダイアログのプロパティー `operation` に設定する。
  3. テンプレートは `@if (operation)` の中身を表示する。`operation` が設定されていないときは何も表示しない。
  4. 取引一覧は `modalRef.closed` を購読し、理由が `ITEM_DELETED_EVENT` のときだけ `load()` を呼ぶ準備をする。
- 状態変化: ダイアログの `operation` に値が入る。
- 遷移: なし（ルートは変わらない）。

#### 5.2.2 Cancel ボタンクリック

- トリガー: `(click)="cancel()"`。
- 処理手順: `cancel()` は `this.activeModal.dismiss()` を呼ぶ。API は呼ばない。
- 状態変化: ダイアログが閉じる。
- 遷移: なし。`dismiss()` で閉じたときは `modalRef.closed` は流れないため、取引一覧は再取得しない。

#### 5.2.3 Delete ボタンクリック（削除の実行）

- トリガー: Delete ボタン（`type="submit"`）によるフォームの送信（`(ngSubmit)="confirmDelete(operation.id)"`）。
- 処理手順:
  1. `confirmDelete(id)` が `this.operationService.delete(id)` を呼び、`DELETE api/operations/{id}` を送る。
  2. 成功（`next`）: `this.activeModal.close(ITEM_DELETED_EVENT)` でダイアログを閉じる。`ITEM_DELETED_EVENT` の値は `'deleted'` である。
  3. 取引一覧は `modalRef.closed` の理由が `ITEM_DELETED_EVENT` であることを確かめ、`load()` を呼ぶ。銀行口座一覧やラベル一覧の削除ダイアログの場合と違い、取引一覧の `load()` は表示済みの行を空にしない（[取引一覧_画面設計書](../一覧/取引一覧_画面設計書.md) の 5.2.2、5.2.5）。
  4. 成功の通知: バックエンドはレスポンスヘッダー `x-jhipstersampleapplicationapp-alert` に翻訳キー `jhipsterSampleApplicationApp.operation.deleted` を、`x-jhipstersampleapplicationapp-params` に ID を返す。`notificationInterceptor` が成功アラートを `AlertService` に追加する。ダイアログには `<jhi-alert />` がないため、アラートは取引一覧の `<jhi-alert />` に表示される。
  5. 失敗: `subscribe` に `error` コールバックはなく、ダイアログは閉じない。`errorHandlerInterceptor` がイベント `jhipsterSampleApplicationApp.httpError` を配信し、ダイアログの `<jhi-alert-error />` にエラーが表示される。
- 状態変化: 成功したときはダイアログが閉じ、取引一覧が再取得する。削除の要求中であることを表す状態はなく、Delete ボタンを無効化する指定もない。
- 遷移: なし。

### 5.3 API呼び出し一覧

| No. | 目的 | メソッド | パス | 要求パラメーター | 応答 | 成功時 | エラー時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 削除 | DELETE | `api/operations/{id}` | パスパラメーター `id`（`operation.id`。`encodeURIComponent` でエンコードする）。本文はない | 204（本文なし）。ヘッダー `x-jhipstersampleapplicationapp-alert`、`x-jhipstersampleapplicationapp-params` | ダイアログを `ITEM_DELETED_EVENT` で閉じる。取引一覧が再取得する。成功アラートが追加される | ダイアログは開いたままで、`<jhi-alert-error />` にエラーを表示する |

補足:

- 呼び出し元は `OperationDeleteDialog.confirmDelete(id)` で、メソッドは `OperationService.delete(id)`（`src/app/entities/operation/service/operation.service.ts`）である。URL の起点は `resourceUrl`（`${serverApiUrl}api/operations`）で、`serverApiUrl` はビルド時定数 `SERVER_API_URL` である（`src/app/config/endpoint.constants.ts`）。
- バックエンドは `OperationResource.deleteOperation(id)`（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/OperationResource.java`）である。`operationRepository.deleteById(id)` を呼び、本文のない 204 と削除のアラートヘッダーを返す。
- ラベルとの結合について: 取引とラベルの多対多は結合テーブル `rel_operation__label` で、列 `operation_id` に外部キー制約 `fk_rel_operation__label__operation_id` がある（バックエンドの `src/main/resources/config/liquibase/changelog/20150805125054_added_entity_constraints_Operation.xml`）。所有側はエンティティ `Operation` の `labels` で、カスケードの指定はない（バックエンドの `src/main/java/io/github/jhipster/sample/domain/Operation.java`）。削除のときに結合テーブルの行を除く処理はリソースクラスには書かれておらず、JPA の動きによる。ラベルが紐づいた取引を削除した場合の応答と画面の表示は、コードからは確認できない。統合テスト `OperationResourceIT.deleteOperation()` が 204 を検証するのは、ラベルを紐づけていない取引である（バックエンドの `src/test/java/io/github/jhipster/sample/web/rest/OperationResourceIT.java`）。
- 要求ヘッダーは `authInterceptor` が `Authorization: Bearer <トークン>` を付ける（トークンがあるとき）。バックエンドは `/api/**` に認証を要求する（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）。
- 401 のときは `authExpiredInterceptor` が現在の URL を `StateStorageService.storeUrl()` で保存し、ログアウトして `/login` へ遷移する。

### 5.4 画面遷移

| 遷移先 | 条件 | トリガー |
| --- | --- | --- |
| なし（ダイアログを閉じる） | Cancel ボタンが押された | `cancel()`（`activeModal.dismiss()`） |
| なし（ダイアログを閉じ、取引一覧が再取得する） | 削除に成功した | Delete ボタン（`activeModal.close(ITEM_DELETED_EVENT)`） |
| ログイン（`/login`） | 削除の要求が 401 を返した | `authExpiredInterceptor` |
