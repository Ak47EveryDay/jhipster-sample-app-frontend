## 2. 機能概要

- 取引（`IOperation`）の一覧をテーブル形式で表示する。
- 一覧は `GET api/operations` で取得する。1 回に 20 件（`ITEMS_PER_PAGE`）をページ単位で取り、テーブルの下端までスクロールすると次のページを同じテーブルに追加する（無限スクロール）。銀行口座一覧とラベル一覧が全件を 1 回で取るのとは違う。
- 取得した各ページはサービスの `operationsResource`（`httpResource`）が保持し、画面はその値をシグナル `operations` の末尾に加える。既に表示しているのと同じ ID の行は加えない。
- クエリパラメーター `eagerload=true` を付けて取得し、バックエンドに銀行口座（`bankAccount`）とラベル（`labels`）を一緒に読み込ませる。ラベルはこの一覧には表示しない。
- 見出し行の ID、Date、Description、Amount、Bank Account の 5 列をクリックして並び替えられる。並び替えの状態はクエリパラメーター `sort` に反映され、画面を再読み込みしても同じ並び順になる。
- 並び替えはバックエンド側で行う。銀行口座一覧やラベル一覧のような画面側の並び替え（`refineData()`）は、この画面にはない。並び替えのたびに一覧を空にして先頭ページから取り直す。
- 「Refresh list」ボタンで再取得する。表示済みの行は置き換えず、応答にあって一覧にない ID の行だけを追加する。
- 「Create a new Operation」ボタンで登録画面へ遷移する。
- 各行に詳細表示、編集、削除の操作がある。削除は確認ダイアログを開き、削除が完了したら再取得する。
- 件数が 0 件のときはテーブルの代わりに「No Operations found」の警告を表示する。
- HTTP エラーは `<jhi-alert-error />` に、登録・更新・削除の成功通知は `<jhi-alert />` に表示する。

## 3. 画面レイアウト

画面は `Main` の `<router-outlet />` の中、`<div class="card jh-card">` の内側に表示される（`src/app/layouts/main/main.html`）。テンプレートのルートは `<div>` 1 つで、その中を上から順に次の領域が占める。

```
見出し領域（<h2 id="page-heading" data-cy="OperationHeading">）
    Operations
    [Refresh list]
    [Create a new Operation]
アラート領域
    <jhi-alert-error />   … エラー
    <jhi-alert />         … 成功通知
検索結果なし領域（#no-result）      … operations().length === 0 のとき
    No Operations found
一覧テーブル領域（#entities）       … 上記以外のとき
    ヘッダー行: ID | Date | Description | Amount | Bank Account | （操作）
    データ行:   id | date | description | amount | bankAccount.name | 表示 | 編集 | 削除
    （データ行の <tbody> に無限スクロールの指定がある）
```

| 領域 | テンプレート上の要素 | 表示条件 | 4 章の対応 |
| --- | --- | --- | --- |
| 見出し領域 | `<h2 id="page-heading" data-cy="OperationHeading">` | 常に | `### 見出し領域` |

### 5.2 イベント詳細

#### 5.2.1 画面初期化

- トリガー: コンポーネントが生成された後の最初の変更検知で、`constructor` 内の 3 つの `effect` が実行される。以後はルートのクエリパラメーター（`sort`）が変わるたびに、3 つ目の `effect` が再実行される。
- 処理手順:
  1. `activatedRouteState`（`queryParamMap` と `data` を `toSignal` にしたもの）の初期値は `activatedRoute.snapshot` の値である。
  2. 3 つ目の `effect` が `untracked()` の中で `fillComponentAttributeFromRoute(queryParamMap, data)` を呼ぶ。`sortState` に `sortService.parseSortParam(params.get(SORT) ?? data[DEFAULT_SORT_DATA])` を設定する。クエリパラメーター `sort` がなければ、ルートの `data.defaultSort`（`id,asc`）を使う。
  3. 続けて `reset()` を呼ぶ。`operations` を空配列に、`links` を `{}` にする。
  4. `load()` が `queryBackend()` を呼ぶ。`queryBackend()` は `{ size: this.itemsPerPage(), eagerload: true }`（`size` は `20`）を `queryObject` として作る。`links` が空（`isFirstFetch()` が真）なので `sort: this.sortService.buildSortParam(this.sortState())` を加え、`this.operationService.operationsParams.set(queryObject)` を実行する。
  5. サービス `OperationsService` の `operationsResource`（`httpResource<RestOperation[]>`）は `operationsParams()` を見てリクエストを組み立てる。値が `undefined` ならリクエストしない。値があれば `{ url: this.resourceUrl, params }` として `GET api/operations` を送る。
  6. 応答が届くと、1 つ目の `effect` が `operationsResource.headers()` を受け取る。`Link` ヘッダー（`headers.get('link')`）があれば `parseLinks.parseAll(linkHeader)` で解析して `links` に設定し、なければ `links` を `{}` にする。
  7. 2 つ目の `effect` が `this.operations.update(...)` を実行する。サービスの `operations` の要素のうち、画面の `operations()` にない ID のものを末尾に加える（`fillComponentAttributesFromResponseBody`）。
- 状態変化: `sortState`、`operations`、`links`、`operationsParams`（サービス）、`isLoading`（`operationsResource.isLoading`）、`operations`（サービスと画面）。
- 遷移: なし。

#### 5.2.2 Refresh list ボタンクリック

- トリガー: `(click)="load()"`。`isLoading()` が `true` の間はボタンが無効である。
- 処理手順: `load()` が `queryBackend()` を呼ぶ。`queryBackend()` は `links` の状態によって、次の 3 つに分かれる。
  1. `links().next` があるとき（次のページがある）: `{ size, eagerload }` に `links().next` を上書きして、次のページを取得する。
  2. `links` が空のとき: `sort` を付けて、先頭ページを取得する。
  3. それ以外（`Link` ヘッダーは受け取ったが `next` がないとき）: `page` も `sort` も付かず、`size` と `eagerload` だけを送る。
- いずれの場合も、応答は 5.2.1 の手順 6、7 と同じように処理される。`reset()` は呼ばれないため、コードからは、このボタンで表示済みの行の内容が更新されたり、行が取り除かれたりすることはないと読める。銀行口座一覧やラベル一覧のように一覧全体を取り直すわけではない。
- 状態変化: `operationsParams`、`isLoading`、`links`、`operations`。
- 遷移: なし。

#### 5.2.3 並び替え（見出し行のクリック）

- トリガー: `jhiSortBy` を持つ `<th>` のクリック。`SortByDirective` はホスト要素の `(click)` で `onClick()` を呼ぶ。
- 処理手順:
  1. `SortByDirective.onClick()` が親の `SortDirective` の `this.sort.sort(this.jhiSortBy())` を呼ぶ。
  2. `SortDirective.sort(field)` は、今の `predicate` と同じ列なら `order` を `asc` と `desc` で反転させ、別の列なら `asc` にする。`sortState` を更新し、`sortChange` に新しい状態を出す。
  3. テンプレートの `(sortChange)="navigateToWithComponentValues($event)"` が `handleNavigation(sortState)` を呼ぶ。
  4. `handleNavigation` はまず `this.links.set({})` にする。続けて `{ sort: this.sortService.buildSortParam(sortState) }` を `queryParamsObj` として作り、`this.router.navigate(['./'], { relativeTo: this.activatedRoute, queryParams: queryParamsObj })` を実行する。URL は `/operation?sort=<列>,<順>` になる（例: `/operation?sort=date,desc`）。
  5. クエリパラメーターが変わると `activatedRouteState` が変わり、5.2.1 と同じ流れで、`operations` が空に戻り、新しい並び順で先頭ページを取り直す。
  6. `SortByDirective` の `effect` は、`<th>` の中の `<fa-icon>` のアイコンを `sortState` に応じて切り替える（対象の列でなければ `faSort`、`asc` なら `faSortUp`、`desc` なら `faSortDown`）。
- 並び替えの実体: 画面に並び替えの処理はない。`sort` はクエリパラメーターでバックエンドに送られ、`OperationResource.getAllOperations()` の `Pageable` に渡る（5.3 の補足）。
- Bank Account 列の注意: 列名は `bankAccount.name` であり、`sort=bankAccount.name,asc` の形で送られる。関連先の列を含む並び替えがバックエンドで正しく働くかは、実行していないため確認できない。バックエンドの統合テスト `OperationResourceIT.getAllOperations()` は `sort=id,desc` を送るが、並び順は検証していない（バックエンドの `src/test/java/io/github/jhipster/sample/web/rest/OperationResourceIT.java`）。
- 状態変化: `sortState`、URL のクエリパラメーター `sort`、5.2.1 と同じシグナル群。
- 遷移: 画面遷移はない（同じルート `/operation` のクエリパラメーターだけが変わる）。

#### 5.2.4 次のページの取得（スクロール）

- トリガー: `<tbody infinite-scroll (scrolled)="loadNextPage()" [infiniteScrollDisabled]="!hasMorePage()" [infiniteScrollDistance]="0">`。`infinite-scroll` は ngx-infinite-scroll の `InfiniteScrollDirective` であり、この 3 つの指定はライブラリーのものである（本リポジトリのコードではない）。`hasMorePage` は `!!this.links().next` なので、`Link` ヘッダーに `next` がないときは `scrolled` が出ないように指定されている。
- 処理手順:
  1. `loadNextPage()` が `load()` を呼ぶ。
  2. `queryBackend()` は `hasMorePage()` が真なので、`{ size, eagerload }` に `this.links().next` を上書きする。`links().next` は、`Link` ヘッダーの `rel="next"` のリンク先 URL から `parseLinkHeader()` で取り出したクエリパラメーター（`page`、`size` など）である（`src/app/shared/jhipster/link-header.ts`）。
  3. 応答は 5.2.1 の手順 6、7 と同じように処理される。新しい行が `operations` の末尾に加わり、`links` が新しい `Link` ヘッダーの内容で置き換わる。
  4. `next` がなくなると `hasMorePage()` が偽になり、`[infiniteScrollDisabled]` によって次のページの取得は止まる。
- 単体テスト `should infinite scroll`（`src/app/entities/operation/list/operation.spec.ts`）は、`loadNextPage()` のあとに `operationsParams()` が `page: '1'` を含むことと、2 ページ目の行を加えて `operations()` の件数が 2 になることを検証している。
- 状態変化: `operationsParams`、`isLoading`、`links`、`operations`。
- 遷移: なし。

#### 5.2.5 Delete ボタンクリック（削除ダイアログを開く）

- トリガー: `(click)="delete(operation)"`。
- 処理手順:
  1. `this.modalService.open(OperationDeleteDialog, { size: 'lg', backdrop: 'static' })` で削除ダイアログを開く。`backdrop: 'static'` は、背景をクリックしてもダイアログを閉じない ng-bootstrap の指定である。
  2. `modalRef.componentInstance.operation = operation` で、削除対象をダイアログに渡す。
  3. `modalRef.closed` を購読する。`closed` はダイアログが `close()` で閉じられたときに流れる Observable である（`dismiss()` で閉じられたときは流れない）。
  4. 理由が `ITEM_DELETED_EVENT`（`'deleted'`）のときだけ `load()` を呼ぶ。`load()` は 5.2.2 と同じ分岐であり、`reset()` は呼ばれない。コードからは、削除した行も表示済みの行として残り、応答にあって一覧にない ID の行だけが追加されると読める。
- 状態変化: ダイアログが開く。削除が確定した場合は、`operationsParams`、`isLoading`、`links`、`operations` が 5.2.2 と同じように変わる。
- 遷移: なし。ダイアログの中の処理（`DELETE api/operations/{id}`）は [取引削除_画面設計書](../削除/取引削除_画面設計書.md) に書く。

#### 5.2.6 リンクによる遷移

- トリガー: Create a new Operation ボタン、ID リンク、View、Edit、Bank Account のリンクのクリック。
- 処理手順: `[routerLink]` に従って遷移する。遷移先のルートには `canActivate: [userRouteAccessService]` がある。
- 遷移先: `/operation/new`、`/operation/:id/view`、`/operation/:id/edit`、`/bank-account/:id/view`。
- 状態変化: この画面は破棄される。破棄のとき `<jhi-alert />`（`Alert`）の `ngOnDestroy()` が `alertService.clear()` を呼ぶ。

### 5.3 API呼び出し一覧

| No. | 目的 | メソッド | パス | 要求パラメーター | 応答 | 成功時 | エラー時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 一覧の取得（先頭ページ、次のページ以降、再取得） | GET | `api/operations` | クエリパラメーター: `size`（`20`）、`eagerload`（`true`）。先頭ページのときは `sort`（`<列>,<asc または desc>`。例: `id,asc`）を加える。次のページのときは `Link` ヘッダーの `next` のクエリパラメーター（`page` など）を上書きする | 200: `IOperation` の配列（`id`、`date`、`description`、`amount`、`bankAccount`、`labels`）。ヘッダー `X-Total-Count`、`Link` | `links` に `Link` ヘッダーの内容を入れ、画面の `operations` にない ID の行を末尾に加える | 表示済みの行はそのまま残る。エラーは `<jhi-alert-error />` に表示される |

補足:

- 呼び出し元は `OperationsService.operationsResource`（`src/app/entities/operation/service/operation.service.ts`）である。URL は `resourceUrl`（`${serverApiUrl}api/operations`）で、`serverApiUrl` はビルド時定数 `SERVER_API_URL` である（`src/app/config/endpoint.constants.ts`）。
- `OperationService.query(req?)` も同じ URL を `HttpClient` の `get` で呼ぶが、この画面は使わない。本体で `OperationService` の `query()` を呼んでいるのはラベルの登録・編集画面である（`src/app/entities/label/update/label-update.ts` の `loadRelationshipsOptions()`）。`partialUpdate()` を呼ぶ箇所は本体にない。
- `eagerload` の効果（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/OperationResource.java`、`getAllOperations(pageable, eagerload)`）: `true` のときは `operationRepository.findAllWithEagerRelationships(pageable)` を呼ぶ。これは `left join fetch operation.bankAccount` のクエリーで 1 ページ分を取り、続けて `left join fetch operation.labels` のクエリーでそのページの取引のラベルを一緒に読み込む（バックエンドの `src/main/java/io/github/jhipster/sample/repository/OperationRepository.java`、`OperationRepositoryWithBagRelationshipsImpl.java`）。`false` のときは `findAll(pageable)` を呼ぶ。引数の既定値は `true` である。銀行口座一覧はユーザー 1 つの関連を 1 つのクエリーで読み込むが、取引は銀行口座とラベルの 2 つの関連を別々のクエリーで読み込む。
- ページングのヘッダー: バックエンドは `PaginationUtil.generatePaginationHttpHeaders(...)` で `X-Total-Count`（総件数）と `Link`（ページへのリンク）を付ける（`OperationResource.getAllOperations()`。`PaginationUtil` はライブラリー jhipster-framework のクラスであり、本リポジトリのコードではない）。ヘッダーの形式は `parseLinkHeader()` の注釈に例がある（`src/app/shared/jhipster/link-header.ts`）。画面は `X-Total-Count` は使わず、`Link` の `next` だけを使う。
- `sort` について: バックエンドの `getAllOperations()` は `Pageable` を受け取るため、`sort` はバックエンドの並び替えに渡る。銀行口座一覧やラベル一覧のようにバックエンドが `sort` を捨てることはない。`bankAccount.name` については 5.2.3 の注意に書いた。
- バックエンドは DTO を使わず、エンティティのクラス `Operation`（バックエンドの `src/main/java/io/github/jhipster/sample/domain/Operation.java`。画面コンポーネントの `Operation` とは別のものである）をそのまま JSON で返す。フロントエンドの `IOperation` は `id`、`date`、`description`、`amount`、`bankAccount`、`labels` を定義し、この画面は `labels` を除く 5 つを使う。
- `date` の変換: サービスの `convertValueFromServer()` は、応答の `date` の文字列を `dayjs()` で dayjs オブジェクトに変換する。バックエンドの統合テスト `OperationResourceIT` は、応答の `date` が `DEFAULT_DATE.toString()` と等しいことを検証している（`DEFAULT_DATE` は `Instant` の値である。バックエンドの `src/test/java/io/github/jhipster/sample/web/rest/OperationResourceIT.java`）。
- 要求ヘッダーは `authInterceptor` が `Authorization: Bearer <トークン>` を付ける（トークンがあるとき）。バックエンドは `/api/**` に認証を要求する（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）。
- エラー時の共通の動きは次のとおりである。
  - 401 のときは `authExpiredInterceptor` が現在の URL を `StateStorageService.storeUrl()` で保存し、ログアウトして `/login` へ遷移する。
  - この画面の API に対する HTTP エラーは `errorHandlerInterceptor` がイベント `jhipsterSampleApplicationApp.httpError` として配信する（配信しないのは 401 で、かつ `message` が空か URL に `api/account` を含む場合だけである）。`AlertError` はステータスに応じた文言を `<jhi-alert-error />` に表示する（404 は `error.url.not.found`、サーバーに到達できないときは `error.server.not.reachable`、400 はレスポンスヘッダーや本文の内容を使う）。
