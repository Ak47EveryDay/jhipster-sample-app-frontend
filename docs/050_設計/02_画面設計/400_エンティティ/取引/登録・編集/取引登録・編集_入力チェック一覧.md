補足:

- エラーメッセージの表示条件: Date と Amount は、コントロールが `invalid` で、かつ `dirty` または `touched` のときだけメッセージのブロックを表示する（`dateRef.invalid && (dateRef.dirty || dateRef.touched)`、`amountRef.invalid && (amountRef.dirty || amountRef.touched)`）。
- 行番号 2 について: `date` に登録されたバリデーターは `Validators.required` のみで、`errors.datetimelocal` を設定する箇所がこのアプリケーションのコードにはない。そのため、このメッセージが表示されることはない。入力欄が `type="datetime-local"` なので、コントロールに入る値は Angular の日時入力の標準の部品が決める（Angular の標準の動きであり、本リポジトリのコードではない）。E2E テストは、入力欄に `2015-08-04T22:33` を入力できることを確認している（`cypress/e2e/entity/operation.cy.ts`）。
- 行番号 5 について: `amount` に登録されたバリデーターは `Validators.required` のみで、`errors.number` を設定する箇所がこのアプリケーションのコードにはない。そのため、このメッセージが表示されることはない。入力欄が `type="number"` なので、コントロールに入る値は Angular の数値入力の標準の部品が、空欄なら `null`、それ以外なら入力値を数値に変換したものにする（Angular の標準の動きであり、本リポジトリのコードではない）。
- 保存ボタンとの関係: Save ボタンは `[disabled]="editForm.invalid || isSaving()"` の間は無効である。`date` か `amount` が未入力なら押せない。保存メソッド `save()` には、入力値を確認する処理は書かれていない。
- ブラウザーの標準の検証: `<form>` に `novalidate` があるため、ブラウザー自身の検証メッセージは使わない。
- 初期状態: 登録のとき `date` の初期値は現在時刻（`YYYY-MM-DDTHH:mm` の文字列）で、`amount` の初期値は `undefined` なので、最初は `amount` の必須エラーの状態である。`dirty` も `touched` も立っていないため、メッセージは表示されない。`labels` の初期値は `[]` である。
- Date の桁数: フォームの `date` は `DATE_TIME_FORMAT`（`YYYY-MM-DDTHH:mm`、`src/app/config/input.constants.ts`）で分まで扱う。編集のときは取得した日時をこの形式でフォームに入れるため、秒以下はフォームに入らない。

## 4. サーバ側チェック

保存（登録は `POST api/operations`、編集は `PUT api/operations/{id}`）が失敗したとき、画面のコンポーネントは何も処理しない（`onSaveError()` は空である）。共通部品がエラーを受け取り、この画面の `<jhi-alert-error />` に危険アラートとして表示する。表示内容は HTTP ステータスと応答の内容で決まる。

| No. | 発生条件（バックエンド） | HTTP ステータス | バックエンドの応答 | 画面の表示 | この画面から発生するか |
| --- | --- | --- | --- | --- | --- |
| 1 | 本文の `date` が `null`（エンティティの `@NotNull`） | 400 | 本文に `fieldErrors`（`objectName`、`field`、`message` の配列）と `message`（`error.validation`）を持つ Problem Details | `AlertError.handleFieldsError()` が項目ごとに危険アラートを追加する。項目名は翻訳キー `jhipsterSampleApplicationApp.operation.date`、文言は翻訳キー `error.<message>` の翻訳文。翻訳がなければ既定文言 `Error on field "<項目名>"` | 通常は発生しない（行番号 1 の必須チェックと保存ボタンの無効化で送信できない） |
| 2 | 本文の `amount` が `null`（エンティティの `@NotNull`） | 400 | 同上（`field` は `amount`） | 同上（項目名は翻訳キー `jhipsterSampleApplicationApp.operation.amount`） | 通常は発生しない（行番号 4 の必須チェックと保存ボタンの無効化で送信できない） |
| 3 | 登録で、本文の `id` が `null` でない | 400 | ヘッダー `x-jhipstersampleapplicationapp-error`（`error.idexists`）、`x-jhipstersampleapplicationapp-params`（`operation`） | 翻訳キー `error.idexists`（「A new {{ entityName }} cannot already have an ID」）。`entityName` は翻訳キー `global.menu.entities.operation`（「Operation」）の翻訳文 | 発生しない（登録の本文の `id` は常に `null` である） |
| 4 | 編集で、本文の `id` が `null` | 400 | ヘッダー `x-jhipstersampleapplicationapp-error`（`error.idnull`）、`x-jhipstersampleapplicationapp-params`（`operation`） | 翻訳キー `error.idnull`（「Invalid ID」） | 発生しない（`id` が `null` なら登録の `POST` を送る） |
| 5 | 編集で、パスの `id` と本文の `id` が一致しない | 400 | ヘッダー `x-jhipstersampleapplicationapp-error`（`error.idinvalid`）、`x-jhipstersampleapplicationapp-params`（`operation`） | 翻訳キー `error.idinvalid`（「Invalid ID」） | 発生しない（パスの `id` は本文の `id` から作る） |
| 6 | 編集で、`id` のレコードが存在しない | 400 | ヘッダー `x-jhipstersampleapplicationapp-error`（`error.idnotfound`）、`x-jhipstersampleapplicationapp-params`（`operation`） | 翻訳キー `error.idnotfound`（「ID cannot be found」） | 発生し得る（この画面を開いた後に、別の操作で対象の取引が削除された場合） |
| 7 | 認証の失敗 | 401 | － | `authExpiredInterceptor` が現在の URL を保存してログアウトし、`/login` へ遷移する | トークンが無効になったとき |
| 8 | サーバーに到達できない | 0 | － | 翻訳キー `error.server.not.reachable`（「Server not reachable」） | 発生し得る |
| 9 | 上記以外の失敗 | 400、500 など | Problem Details（`message`、`detail`、`params` など） | 本文の `message` を翻訳キーとして表示する（`detail` を既定文言、`params` を埋め込み値にする）。`message` がなければ本文を原文のまま表示する | コードからは確認できない |

補足:

- バックエンド側の定義は次のとおりである。
  - `OperationResource.createOperation()` と `OperationResource.updateOperation()` は、本文を `@Valid @RequestBody Operation` で受け取る（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/OperationResource.java`）。
  - エンティティの `date` と `amount` には `@NotNull` が付いている。`description`、`bankAccount`、`labels` には必須の制約がない（バックエンドの `src/main/java/io/github/jhipster/sample/domain/Operation.java`）。
  - `@Valid` 違反は `ExceptionTranslator` が 400 に変換し、本文に `fieldErrors` を入れる。`message` にはデフォルトメッセージ、それが空なら制約名（コード）を入れる（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/ExceptionTranslator.java`）。
  - `BadRequestAlertException` は 400 と、ヘッダー `x-jhipstersampleapplicationapp-error`、`x-jhipstersampleapplicationapp-params` を返す（同 `ExceptionTranslator.java` の `buildHeaders()`）。
  - 統合テスト `OperationResourceIT` の `checkDateIsRequired()` と `checkAmountIsRequired()` は、それぞれ `date`、`amount` が `null` の登録が 400 になることを検証している（バックエンドの `src/test/java/io/github/jhipster/sample/web/rest/OperationResourceIT.java`）。
- 行番号 1、2 の文言について: バックエンドの統合テスト `ExceptionTranslatorIT`（バックエンドの `src/test/java/io/github/jhipster/sample/web/rest/errors/ExceptionTranslatorIT.java`）は、`@NotNull` 違反の `fieldErrors` の `message` が `must not be null` になることを検証している。このときの翻訳キー `error.must not be null` は `src/i18n/en/global.json` にない（あるのは `error.NotNull` と `error.Size` である）。そのため、画面には既定文言 `Error on field "Date"`、`Error on field "Amount"` が出るとコードから読める。実機での表示は確認していない。
- 日時の形式について: この画面が送る `date` は dayjs の `toJSON()` による ISO 8601 形式の文字列であり、形式の誤った日時を送る経路は画面にはない。形式の誤った本文を受けたときのバックエンドの応答と画面の表示は、コードからは確認できない。
- 桁数について: データベースの定義では `date` の列の型はプロパティー `datetimeType` で決まり H2 では `datetime(6)`、PostgreSQL では `datetime` である（バックエンドの `src/main/resources/config/liquibase/master.xml`）。`description` は `varchar(255)`、`amount` は `decimal(21,2)`、`bank_account_id` は `bigint` である（バックエンドの `src/main/resources/config/liquibase/changelog/20150805125054_added_entity_Operation.xml`）。桁数を超えた場合や、`amount` に小数第 3 位以下を入力した場合の扱いは、コードからは確認できない（Bean Validation にも画面にも桁数のチェックがない）。
- 関連について: `bankAccount` と `labels` の要素はバックエンドから取得した選択肢から選ぶため、画面に存在しない ID を送る経路はない。保存のときに選んだ銀行口座やラベルが存在しなくなっている場合の応答は、コードからは確認できない。
- エラー時の共通の動き: 保存が失敗しても画面は遷移せず、`isSaving` が `false` に戻って保存ボタンが再び有効になる（`src/app/entities/operation/update/operation-update.ts` の `subscribeToSaveResponse()`、`onSaveFinalize()`）。
