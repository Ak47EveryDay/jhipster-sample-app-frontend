## 2. 機能概要

- 1 つの画面で登録（`/operation/new`）と編集（`/operation/:id/edit`）の両方を担う。どちらであるかは、フォームの `id` の値が `null` かどうかで区別する。
- 編集のときは、ルートのリゾルバー `operationResolve` が `GET api/operations/{id}` で取得した取引をフォームに設定する。登録のときはリゾルバーが API を呼ばずに `null` を返し、フォームは既定値（`id` は `null`、Date は画面を開いた時刻、Label は空配列）で始まる。
- 入力項目は Date、Description、Amount、Bank Account、Label の 5 つである。ID は編集のときだけ読み取り専用で表示する。
- Date と Amount は必須である。登録の初期状態では Date に現在時刻が入っているため、Amount が未入力の間はフォームは無効である。
- Bank Account は単一選択のリストから選ぶ。選択肢は `GET api/bank-accounts` で取得した銀行口座に、編集対象が持つ銀行口座を加えたものである。先頭に未選択の空欄がある。
- Label は複数選択のリストで、紐づけるラベルを選ぶ。選択肢は `GET api/labels` で取得したラベルに、編集対象が持つラベルを加えたものである。空欄の選択肢はなく、何も選ばなければ空配列になる。
- 関連の 2 つの選択肢は、画面を開いたときにそれぞれ 1 回ずつ取得する（`loadRelationshipsOptions()`）。引数を付けないため、クエリパラメーターはない。
- フォームが無効な間と保存中は、保存ボタンが無効になる。
- 保存は、登録なら `POST api/operations`、編集なら `PUT api/operations/{id}` を送る。本文では Date は ISO 8601 形式の文字列になり、Bank Account は選んだ銀行口座のオブジェクト（未選択なら `null`）、Label は選んだラベルのオブジェクトの配列になる。成功したらブラウザーの履歴を 1 つ戻る。
- 保存に失敗したら画面にとどまり、エラーを `<jhi-alert-error />` に表示する。保存ボタンは再び有効になる。
- Cancel ボタンでブラウザーの履歴を 1 つ戻る。入力内容を破棄するかどうかの確認はしない。
- この画面には `<jhi-alert />` がない。保存の成功通知は、戻った先の画面の `<jhi-alert />` に表示される。

## 3. 画面レイアウト

画面は `Main` の `<router-outlet />` の中に表示される（`src/app/layouts/main/main.html`）。テンプレートは中央寄せの `<div class="d-flex justify-content-center">` と `<div class="col-8">` で囲み、その中に `<form name="editForm" novalidate (ngSubmit)="save()" [formGroup]="editForm">` を置く。フォームの中を上から順に次の領域が占める。

```
見出し領域（<h2>、id="jhi-operation-heading"）
    Create or edit a Operation
アラート領域
    <jhi-alert-error />
入力フォーム領域
    ID           … 編集のときだけ表示（読み取り専用）
    Date         … 日時入力欄                [This field is required.]
    Description  … テキストボックス
    Amount       … 数値ボックス              [This field is required.]
    Bank Account … 選択リスト（空欄 + 銀行口座の一覧）
    Label        … 複数選択リスト（ラベルの一覧）
ボタン領域
    [Cancel] [Save]
```

### 5.2 イベント詳細

#### 5.2.1 画面初期化

- トリガー: `/operation/new` または `/operation/:id/edit` への遷移。
- 処理手順:
  1. ルートガード `userRouteAccessService` がアカウントを確認する。未ログインなら遷移前の URL を保存して `/login` へ遷移し、ここで終わる。
  2. リゾルバー `operationResolve(route)` が動く。`/operation/new` には `id` がないため `of(null)` を返し、API を呼ばない。`/operation/:id/edit` では `OperationService.find(id)` で `GET api/operations/{id}` を送る。失敗したときは 404 なら `/404`、それ以外なら `/error` へ遷移して `EMPTY` を返す。
  3. コンポーネントのフィールド初期化で `this.operationFormService.createOperationFormGroup()` が引数なしで実行され、フォームグループ `editForm` ができる。この時点の値は `id` が `null`、`date` が現在時刻を `YYYY-MM-DDTHH:mm` にした文字列、`description` が `undefined`、`amount` が `undefined`、`bankAccount` が `undefined`、`labels` が `[]` である。`amount` は必須のため、この時点のフォームは無効である。
  4. `ngOnInit()` が `this.activatedRoute.data` を購読し、`data.operation`（リゾルバーの結果）を受け取る。
  5. `operation` が真（編集）なら `updateForm(operation)` を呼ぶ。`this.operation` に代入し、`this.operationFormService.resetForm(this.editForm, operation)` でフォームに値を設定する。続けて `bankAccountsSharedCollection` に対し、`operation.bankAccount` がまだ選択肢になければそれを先頭に加える（`bankAccountService.addBankAccountToCollectionIfMissing`）。同様に `labelsSharedCollection` に対し、`operation.labels ?? []` のうちまだ選択肢にないものを先頭に加える（`labelService.addLabelToCollectionIfMissing`）。
  6. `operation` が `null`（登録）なら `updateForm` を呼ばず、手順 3 の既定値のまま使う。
  7. `loadRelationshipsOptions()` が 2 つの要求を出す。どちらも引数がないため、クエリパラメーターは付かない。
     - `this.bankAccountService.query()` で `GET api/bank-accounts` を送る。応答の本文（`res.body ?? []`）に対し、`this.operation?.bankAccount` がなければそれを加え、`bankAccountsSharedCollection.set(bankAccounts)` で選択肢を置き換える。
     - `this.labelService.query()` で `GET api/labels` を送る。応答の本文に対し、`this.operation?.labels ?? []` のうちまだなければそれを加え、`labelsSharedCollection.set(labels)` で選択肢を置き換える。
- フォームサービス `OperationFormService` の働き:
  - `createOperationFormGroup(operation?)`: 既定値と引数（なければ `{ id: null }`）をマージし、`convertOperationToOperationRawValue()` を通してから `FormGroup` を作る。コントロールは次の 6 つである。
    - `id`: 初期値はマージ結果の `id`。`disabled: true`、`nonNullable: true`、`validators: [Validators.required]`。
    - `date`: 初期値はマージ結果の `date`（文字列）。`validators: [Validators.required]`。
    - `description`: 初期値はマージ結果の `description`。バリデーターはない。
    - `amount`: 初期値はマージ結果の `amount`。`validators: [Validators.required]`。
    - `bankAccount`: 初期値はマージ結果の `bankAccount`。バリデーターはない。
    - `labels`: 初期値はマージ結果の `labels`（なければ `[]`）。バリデーターはない。
  - `getFormDefaults()`: `id` が `null`、`date` が `dayjs()`（このメソッドを呼んだ時点の現在時刻）、`labels` が `[]` のオブジェクトを返す。
  - `convertOperationToOperationRawValue(operation)`: `date` を dayjs オブジェクトから `DATE_TIME_FORMAT`（`YYYY-MM-DDTHH:mm`）の文字列に変換する（`date` がなければ `undefined`）。`labels` がなければ `[]` にする。
  - `convertOperationRawValueToOperation(rawOperation)`: その逆の変換で、`date` を `dayjs(rawOperation.date, DATE_TIME_FORMAT)` で dayjs オブジェクトにする。
  - `resetForm(form, operation)`: 既定値と引数をマージし、`convertOperationToOperationRawValue()` を通した値で `form.reset()` を呼ぶ。`id` は `id: { value: operationRawValue.id, disabled: true }` として渡し、無効の状態を保つ。
  - `getOperation(form)`: `form.getRawValue()` を `convertOperationRawValueToOperation()` に通す。無効なコントロール（`id`）の値も含まれる。
- 日時の扱い: 銀行口座の登録・編集には日時の項目がないため、この変換は取引だけのものである。フォームの `date` は入力欄（`type="datetime-local"`）に合わせた `YYYY-MM-DDTHH:mm` の文字列で持ち、モデルの `date` は dayjs オブジェクトで持つ。編集のときは取得した日時を分までの文字列に整形するため、秒以下はフォームに入らない。`DATE_TIME_FORMAT` は `src/app/config/input.constants.ts` にあり、日付の解析に使う `customParseFormat` は `src/app/config/dayjs.ts` で dayjs に追加している。
- 登録と編集の判定: テンプレートは `editForm.controls.id.value !== null` のときだけ ID 入力欄を表示する。`save()` は `getOperation()` で取り出した値の `id` が `null` なら登録（`create`）、そうでなければ編集（`update`）として扱う。
- 選択肢と選択状態の対応づけ: `<select>` の `[compareWith]` は、Bank Account が `compareBankAccount`（`BankAccountService.compareBankAccount()`）、Label が `compareLabel`（`LabelService.compareLabel()`）であり、`id` が等しければ同じものとみなす。編集のときはフォームの `bankAccount` と `labels` に取得した値が入り、`id` で選択肢と対応づけられる（`compareWith` による対応づけは Angular の標準の動きであり、本リポジトリのコードではない）。
- 状態変化: `operation`、`editForm` の各コントロールの値、`bankAccountsSharedCollection`、`labelsSharedCollection`。
- 遷移: 通常はなし。編集でリゾルバーが失敗したときだけ `/404` または `/error` へ遷移する。

#### 5.2.2 入力（Date、Description、Amount、Bank Account、Label）

- トリガー: 各入力欄への入力、Bank Account と Label の選択の変更。
- 処理手順: Reactive Forms がコントロールの値を更新し、バリデーターを評価し直す。この画面には入力時のメソッド呼び出しはない。
- 状態変化: `editForm` の各コントロールの値と、`invalid`、`dirty`、`touched` の状態。
- 表示の変化:
  - Date: `dateRef.invalid && (dateRef.dirty || dateRef.touched)` のとき、`dateRef.errors?.required` なら翻訳キー `entity.validation.required`（「This field is required.」）を表示する。`[hidden]="!dateRef.errors?.datetimelocal"` で翻訳キー `entity.validation.datetimelocal`（「This field should be a date and time.」）を表示する要素もあるが、`datetimelocal` エラーを設定するバリデーターはコード上にない（入力チェック一覧の 2 章参照）。
  - Description: エラーメッセージの表示はない。
  - Amount: `amountRef.invalid && (amountRef.dirty || amountRef.touched)` のとき、`amountRef.errors?.required` なら翻訳キー `entity.validation.required` を表示する。`[hidden]="!amountRef.errors?.number"` で翻訳キー `entity.validation.number`（「This field should be a number.」）を表示する要素もあるが、`number` エラーを設定するバリデーターはコード上にない（入力チェック一覧の 2 章参照）。
  - Bank Account、Label: エラーメッセージの表示はない。
  - Save ボタン: `editForm.invalid || isSaving()` が真の間は無効である。登録の初期状態では `date` に現在時刻が入っているため、`amount` が未入力の間は無効である。
- 遷移: なし。

#### 5.2.3 Cancel ボタンクリック

- トリガー: `(click)="previousState()"`。
- 処理手順: `previousState()` は `globalThis.history.back()` を呼ぶだけである。入力内容の破棄を確認する処理はない。
- 状態変化: なし（画面が破棄される）。
- 遷移: ブラウザーの履歴を 1 つ戻る。遷移先は履歴による（取引一覧から来たなら取引一覧に戻る）。履歴がない場合の遷移先は、コードからは確認できない。

#### 5.2.4 Save ボタンクリック（保存）

- トリガー: Save ボタン（`type="submit"`）によるフォームの送信（`(ngSubmit)="save()"`）。ボタンは `editForm.invalid || isSaving()` の間は無効である。
- 処理手順:
  1. `this.isSaving.set(true)` にする。
  2. `this.operationFormService.getOperation(this.editForm)` で `form.getRawValue()` を取り出し、`date` を dayjs オブジェクトに変換する。中身は `id`、`date`、`description`、`amount`、`bankAccount`、`labels` である。
  3. `operation.id === null` なら `this.operationService.create(operation)`（`POST api/operations`）を、そうでなければ `this.operationService.update(operation)`（`PUT api/operations/{id}`）を呼ぶ。`PUT` のパスの `id` は本文の `id`（`getOperationIdentifier(operation)`）である。サービスの `create()` と `update()` は送信前に `convertValueFromClient()` を呼び、`date` を `toJSON()` で文字列にする。
  4. `subscribeToSaveResponse(result)` が結果を購読する。
     - 成功（`next`）: `onSaveSuccess()` が `previousState()` を呼び、ブラウザーの履歴を 1 つ戻る。応答本文は使わない。
     - 失敗（`error`）: `onSaveError()` は何もしない（コメント「Api for inheritance.」）。
     - 成功・失敗とも（`finalize`）: `onSaveFinalize()` が `this.isSaving.set(false)` を実行し、保存ボタンを再び有効にする。
  5. 成功の通知: バックエンドはレスポンスヘッダー `x-jhipstersampleapplicationapp-alert` に翻訳キー（登録は `jhipsterSampleApplicationApp.operation.created`、編集は `jhipsterSampleApplicationApp.operation.updated`）を、`x-jhipstersampleapplicationapp-params` に ID を返す。`notificationInterceptor` がこれを成功アラートとして `AlertService` に追加する。この画面には `<jhi-alert />` がないため、アラートは戻った先の画面の `<jhi-alert />` に表示される（取引一覧と取引詳細にはある）。
  6. 失敗の通知: `errorHandlerInterceptor` がイベント `jhipsterSampleApplicationApp.httpError` を配信し、この画面の `<jhi-alert-error />` にエラーが表示される。エラーごとの表示内容は [取引登録・編集_入力チェック一覧](./取引登録・編集_入力チェック一覧.md) の 4 章に書く。
- 状態変化: `isSaving`（`true` にしたあと `false` に戻る）。フォームの値は変更しない。
- 遷移: 保存に成功したときだけブラウザーの履歴を 1 つ戻る。

補足:

- 呼び出し元は次のとおりである。
  - No. 1: リゾルバー `operationResolve`（`src/app/entities/operation/route/operation-routing-resolve.service.ts`）の `OperationService.find(id)`。
  - No. 2: `OperationUpdate.loadRelationshipsOptions()` の `BankAccountService.query()`（`src/app/entities/bank-account/service/bank-account.service.ts`）。引数がないためクエリパラメーターは付かない。
  - No. 3: 同メソッドの `LabelService.query()`（`src/app/entities/label/service/label.service.ts`）。引数がないためクエリパラメーターは付かない。
  - No. 4、5: `OperationUpdate.save()` の `OperationService.create()`、`OperationService.update()`。URL の起点は `resourceUrl`（`${serverApiUrl}api/operations`）で、`serverApiUrl` はビルド時定数 `SERVER_API_URL` である（`src/app/config/endpoint.constants.ts`）。
- 本文の `date`: フォームの日時（`YYYY-MM-DDTHH:mm`）から `dayjs()` で作った dayjs オブジェクトを、サービスの `convertValueFromClient()` が `toJSON()` で文字列にする。`toJSON()` は dayjs のメソッドであり、ISO 8601 形式の文字列を返す（ライブラリーの動きであり、本リポジトリのコードではない）。`date` がなければ `null` になるが、必須チェックのため `null` で送ることはない。
- 本文の `bankAccount` にはフォームコントロール `bankAccount` の値がそのまま入る。選択肢から選んだ場合は `GET api/bank-accounts` の要素、編集で選択し直さなかった場合は `GET api/operations/{id}` の応答にあった `bankAccount` のオブジェクト、未選択の場合は `null` である。フロントエンドの型は `IBankAccount`（`id`、`name`、`balance`、`user`）である（`src/app/entities/bank-account/bank-account.model.ts`）。
- 本文の `labels` にはフォームコントロール `labels` の値がそのまま入る。選択したラベルのオブジェクト（`ILabel`）の配列であり、未選択なら `[]` である。ラベルの登録・編集画面が `operations` として送る形と同じである。
- No. 2 のバックエンドは `BankAccountResource.getAllBankAccounts(eagerload)`（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/BankAccountResource.java`）である。ページングはなく全件を返す。フロントエンドは `eagerload` を指定しないため引数の既定値 `true` になり、`bankAccountRepository.findAllWithEagerRelationships()` で各銀行口座のユーザーも一緒に読み込む（この画面は選択肢の表示に `name` だけを使う）。
- No. 3 のバックエンドは `LabelResource.getAllLabels()`（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/LabelResource.java`）である。ページングはなく全件を返す（`labelRepository.findAll()`）。銀行口座の登録・編集画面の User の選択肢（`GET api/users`）やラベルの登録・編集画面の Operation の選択肢（`GET api/operations`）がページ単位で返るのとは違い、この 2 つの選択肢は全件が対象になる。
- No. 4、5 のバックエンドの `OperationResource`（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/OperationResource.java`）の確認事項:
  - `createOperation`: `@Valid @RequestBody Operation` を受け取る。`id` が `null` でなければ 400（`idexists`）を返す。保存に成功したら 201 と、`Location` ヘッダー（`new URI("/api/operations/" + operation.getId())`）を返す。
  - `updateOperation`: パスの `id` と `@Valid @RequestBody Operation` を受け取る。本文の `id` が `null` なら 400（`idnull`）、パスと本文の `id` が一致しなければ 400（`idinvalid`）、ID のレコードが存在しなければ 400（`idnotfound`）を返す。保存に成功したら 200 を返す。
  - `@Valid` により、エンティティのクラス `Operation`（バックエンド）の `date` と `amount` の `@NotNull` 違反は 400 になる。`bankAccount` と `labels` には `@NotNull` がない。
  - 400 のうち `BadRequestAlertException` によるものは、レスポンスヘッダー `x-jhipstersampleapplicationapp-error`（`error.<errorKey>`）と `x-jhipstersampleapplicationapp-params`（`operation`）を返す。ヘッダー名は大文字と小文字を区別しないため、フロントエンドの定数（`src/app/shared/jhipster/constants.ts`）の小文字の表記と一致する。
- 関連の保存について: エンティティ `Operation` の `bankAccount` は多対 1（`@ManyToOne(fetch = FetchType.LAZY)`）、`labels` は多対多の所有側（`@JoinTable` の名前は `rel_operation__label`）である（バックエンドの `src/main/java/io/github/jhipster/sample/domain/Operation.java`）。`createOperation` と `updateOperation` は `operationRepository.save(operation)` を呼ぶ。ラベルの登録・編集画面が送る `operations` は多対多の被所有側であるが、この画面が送る `labels` は所有側である。結合テーブルの行がどのように更新されるかは JPA の動きであり、本リポジトリのコードには書かれていない。
- 要求ヘッダーは `authInterceptor` が `Authorization: Bearer <トークン>` を付ける（トークンがあるとき）。バックエンドは `/api/**` に認証を要求する（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`）。
- 401 のときは `authExpiredInterceptor` が現在の URL を `StateStorageService.storeUrl()` で保存し、ログアウトして `/login` へ遷移する。
