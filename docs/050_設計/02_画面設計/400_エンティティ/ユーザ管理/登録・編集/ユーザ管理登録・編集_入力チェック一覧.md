補足:

- エラーメッセージの表示条件: 各コントロールが `invalid` で、かつ `dirty` または `touched` のときだけメッセージのブロックを表示する（例: `loginRef.invalid && (loginRef.dirty \|\| loginRef.touched)`）。
- メッセージは 1 つの項目について同時に複数出せる。Login に 51 文字以上の日本語を入力した場合は、最大長と形式の 2 つのメッセージが出る。
- 保存ボタンとの関係: Save ボタンは `[disabled]="editForm.invalid \|\| isSaving()"` の間は無効である。Login が未入力、または Email が未入力・形式不正のときは押せない。保存メソッド `save()` には、入力値を確認する処理は書かれていない。
- ブラウザーの標準の検証: `<form>` に `novalidate` があるため、ブラウザー自身の検証メッセージは使わない。Email の入力欄は `type="text"` であり、`type="email"` ではない。
- 初期状態:
  - 登録のとき、Login の初期値は `null` で Email の初期値はないため、最初から必須エラーの状態である。`dirty` も `touched` も立っていないため、メッセージは表示されないが、Save ボタンは無効である。
  - 編集のときは、リゾルバーが取得した値がフォームに入る。Login と Email に値があれば、保存できる状態になる。
- 行番号 3 の正規表現について: 画面のパターンは、メールアドレス形式のパターンと、英数字と `_`、`.`、`@`、`-` だけの文字列のパターンを、縦棒（正規表現の OR）で結んだものである（`src/app/entities/admin/user-management/update/user-management-form.service.ts` の `login` の `Validators.pattern`）。バックエンドの `Constants.LOGIN_REGEX`（バックエンドの `src/main/java/io/github/jhipster/sample/config/Constants.java`）は同じ 2 つのパターンを含み、先頭に `^`、末尾に `$` を持ち、それぞれをかっこでグループ化して並べる点が違うだけである。画面のパターンは全体を `^` と `$` で挟んでいるため、メールアドレス形式のパターンは先頭のみ、英数字のパターンは末尾のみに位置の制約が付くと読める。

## 4. サーバ側チェック

補足:

- バックエンド側の定義は次のとおりである。
  - `UserResource.createUser()` と `UserResource.updateUser()` は、本文を `@Valid @RequestBody AdminUserDTO` で受け取る（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/UserResource.java`）。
  - `AdminUserDTO` の制約は行番号 5 から 8 のとおりである（バックエンドの `src/main/java/io/github/jhipster/sample/service/dto/AdminUserDTO.java`）。
  - `@Valid` 違反は `ExceptionTranslator` が 400 に変換し、本文に `fieldErrors` を入れる（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/ExceptionTranslator.java` の `getFieldErrors()`）。
  - `fieldErrors` の `objectName` は、Spring が本文の引数に付ける名前から末尾の `DTO` を除いたものである（`getFieldErrors()` の `f.getObjectName().replaceFirst("DTO$", "")`）。引数の名前はコードからは確認できないため、実際の値も確認できない。`jhipsterSampleApplicationApp.<objectName>.login` の形の翻訳キーは `src/i18n/en/user-management.json` にはなく（同ファイルのキーは `jhipsterSampleApplicationApp` を挟まない `userManagement.<項目>` の形である）、項目名は翻訳できないと読める。実機での表示は確認していない。
  - `LoginAlreadyUsedException` と `EmailAlreadyUsedException` は `BadRequestAlertException` を継承する。エンティティ名はどちらも `userManagement` であり、エラーキーは `userexists` と `emailexists` である（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/LoginAlreadyUsedException.java`、`EmailAlreadyUsedException.java`）。本文には `message`（`error.` とエラーキーを繋いだもの）と `params`（エンティティ名）が入り、`ExceptionTranslator.buildHeaders()` がヘッダー `x-jhipstersampleapplicationapp-error` と `x-jhipstersampleapplicationapp-params` を付ける（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/errors/BadRequestAlertException.java`、`ExceptionTranslator.java`）。画面ではヘッダーに `params` があるため、`entityName` に翻訳キー `global.menu.entities.userManagement` の翻訳文を埋め込もうとするが、この翻訳キーは定義されていない。
- 画面のチェックとバックエンドの制約の違い:
  - Email の最大長は、画面は 191 であり、バックエンドは 254 である。画面のほうが厳しい。
  - Email の最小長は、画面もバックエンドも 5 である。
  - `langKey` は、バックエンドは 2 文字以上を要求するが、画面は最大長（10）しかチェックしない。
- 登録のとき選んだ Profiles は、バックエンドが各権限名で `authorityRepository.findById()` を行い、存在するものだけをユーザーに付与する（バックエンドの `src/main/java/io/github/jhipster/sample/service/UserService.java` の `createUser()`）。存在しない権限名を送ってもエラーにはならない。
- エラー時の共通の動き: 保存が失敗しても画面は遷移せず、`isSaving` が `false` に戻って保存ボタンが再び有効になる（`src/app/entities/admin/user-management/update/user-management-update.ts` の `subscribeToSaveResponse()`、`onSaveFinalize()`）。
