## 2. 機能概要

- ユーザー（`IUserManagement`）の一覧をテーブル形式で表示する。管理者用の画面である。
- 一覧は `GET api/admin/users` で取得する。ページングがあり、1 ページ 20 件である。
- 取得した一覧はサービスの `userManagementsResource`（`httpResource`）が保持し、画面はその値をシグナル `userManagements` に写す。並び替えは画面では行わない（バックエンドで並び替えたとおりに表示する）。
- ページの下に、表示中の範囲（「Showing 1 - 20 of 45 items.」など）とページ送りのボタンを表示する。
- 見出し行の Login、Email、Language、Created date、Modified by、Modified date の 6 列をクリックして並び替えられる。並び替えの状態はクエリパラメーター `sort` に反映され、バックエンドが並び替える。
- 各行には、有効・無効を切り替えるボタンと、詳細表示、編集、削除の操作がある。
- ログイン中のユーザー自身の行では、無効化と削除のボタンが無効である。
- Profiles の列は、ユーザーの権限を権限詳細へのリンクとして表示する。
- 「Refresh list」ボタンで一覧を再取得する。「Create a new user」ボタンで登録画面へ遷移する。
- 件数が 0 件のときはテーブルの代わりに「No user found」の警告を表示する。
- HTTP エラーは `<jhi-alert-error />` に、更新・削除の成功通知は `<jhi-alert />` に表示する。

## 3. 画面レイアウト

画面は `Main` の `<router-outlet />` の中、`<div class="card jh-card">` の内側に表示される（`src/app/layouts/main/main.html`）。テンプレートのルートは `<div>` 1 つである。

```
見出し領域（<h2 id="page-heading" data-cy="UserManagementHeading">）
    Users
    [Refresh list]
    [Create a new user]
アラート領域
    <jhi-alert-error />   … エラー
    <jhi-alert />         … 成功通知
検索結果なし領域（#no-result）          … userManagements().length === 0 のとき
    No user found
一覧テーブル領域（#entities）            … 上記以外のとき
    ヘッダー行: Login | Email | （見出しなし） | Language | Created date | Modified by | Modified date | Profiles | （操作）
    データ行:   login | email | [Activated] または [Deactivated] | langKey | createdDate | lastModifiedBy | lastModifiedDate | 権限のリンク | 表示 | 編集 | 削除
ページ送り領域                           … userManagements().length > 0 のとき
    Showing 1 - 20 of 45 items.
    [«] [<] 1 2 3 4 5 [>] [»]
```

| 領域 | テンプレート上の要素 | 表示条件 | 4 章の対応 |
| --- | --- | --- | --- |
| 見出し領域 | `<h2 id="page-heading" data-cy="UserManagementHeading">` | 常に | `### 見出し領域` |
| アラート領域 | `<jhi-alert-error />`、`<jhi-alert />` | 常に（アラートがあるときだけ内容が表示される） | `### アラート領域` |
| 検索結果なし領域 | `<div class="alert alert-warning" id="no-result">` | `userManagements().length === 0` | `### 検索結果なし領域` |
| 一覧テーブル領域 | `<div class="table-responsive table-entities" id="entities">` の中の `<table>` | `userManagements().length === 0` 以外（`@else`） | `### 一覧テーブル領域・ヘッダー行`、`### 一覧テーブル領域・データ行` |
| ページ送り領域 | `<jhi-item-count>`（`ItemCount`）と `<ngb-pagination>` | `userManagements().length > 0` | `### ページ送り領域` |

### 5.2 イベント詳細

#### 5.2.1 画面初期化

- トリガー: コンポーネントが生成された後の最初の変更検知で、`constructor` 内の 3 つの `effect` が実行される。以後はルートのクエリパラメーター（`page`、`sort`）が変わるたびに、3 つ目の `effect` が再実行される。
- 処理手順:
  1. `activatedRouteState`（`queryParamMap` と `data` を `toSignal` にしたもの）の初期値は `activatedRoute.snapshot` の値である。
  2. 3 つ目の `effect` が `untracked()` の中で `fillComponentAttributeFromRoute(queryParamMap, data)` を呼ぶ。
     - `page` はクエリパラメーター `page` を数値にしたもの。なければ `1` である。
     - `sortState` に `sortService.parseSortParam(params.get(SORT) ?? data[DEFAULT_SORT_DATA])` を設定する。クエリパラメーター `sort` がなければ、ルートの `data.defaultSort` を使うが、このルートには `defaultSort` の定義がないため、`sortState` は `{ predicate: undefined }` になる。
  3. 続けて `load()` を呼ぶ。`load()` は `queryBackend()` を呼ぶ。`queryBackend()` は `{ page: this.page() - 1, size: this.itemsPerPage(), sort: this.sortService.buildSortParam(this.sortState()) }` を `queryObject` として作り、`this.userManagementService.userManagementsParams.set(queryObject)` を実行する。ページ番号はバックエンド向けに 1 つ減らす（バックエンドは 0 から始まる）。
  4. サービス `UserManagementsService` の `userManagementsResource`（`httpResource<RestUserManagement[]>`）は `userManagementsParams()` を見てリクエストを組み立てる。値が `undefined` ならリクエストしない。値があれば `{ url: this.resourceUrl, params }` として `GET api/admin/users` を送る。
  5. 応答が届くと `userManagementsResource` の値が変わり、`computed` である `userManagements`（サービス）が変わる。値は `convertValueFromServer()` を通り、`createdDate` と `lastModifiedDate` の文字列が dayjs のオブジェクトになる。
  6. 2 つ目の `effect` が `this.userManagements.set(this.fillComponentAttributesFromResponseBody([...this.userManagementService.userManagements()]))` を実行する。`fillComponentAttributesFromResponseBody()` はデータをそのまま返す（画面では並び替えない）。
  7. 1 つ目の `effect` がレスポンスヘッダーを読み、`totalItems` に `X-Total-Count` ヘッダーの値を数値にしたものを設定する。
- 状態変化: `page`、`sortState`、`userManagementsParams`（サービス）、`isLoading`（`userManagementsResource.isLoading`）、`userManagements`（サービスと画面）、`totalItems`。
- 遷移: なし。

#### 5.2.2 Refresh list ボタンクリック

- トリガー: `(click)="load()"`。`isLoading()` が `true` の間はボタンが無効である。
- 処理手順: `load()` が `queryBackend()` を呼び、`userManagementsParams` に新しいオブジェクトを設定する。以後は 5.2.1 の手順 4 から 7 と同じである。
- 状態変化: `userManagementsParams`、`isLoading`、`userManagements`、`totalItems`。
- 遷移: なし。

#### 5.2.3 並び替えとページの移動

- トリガー: 並び替えは `jhiSortBy` を持つ `<th>` のクリック。ページの移動は `<ngb-pagination>` の `(pageChange)`。
- 処理手順（並び替え）:
  1. `SortByDirective.onClick()` が親の `SortDirective` の `this.sort.sort(this.jhiSortBy())` を呼ぶ。
  2. `SortDirective.sort(field)` は、今の `predicate` と同じ列なら `order` を `asc` と `desc` で反転させ、別の列なら `asc` にする。`sortState` を更新し、`sortChange` に新しい状態を出す。
  3. テンプレートの `(sortChange)="navigateToWithComponentValues($event)"` が `handleNavigation(this.page(), sortState)` を呼ぶ。
  4. `handleNavigation()` は `{ page, size: this.itemsPerPage(), sort: this.sortService.buildSortParam(sortState) }` を `queryParamsObj` として作り、`this.router.navigate(['./'], { relativeTo: this.activatedRoute, queryParams: queryParamsObj })` を実行する。URL は `/user-management?page=<番号>&size=20&sort=<列>,<順>` になる。
  5. クエリパラメーターが変わると `activatedRouteState` が変わり、5.2.1 と同じ流れで再取得が行われる。ページは今のページのままである。
- 処理手順（ページの移動）: `navigateToPage(page)` が `handleNavigation(page, this.sortState())` を呼ぶ。以後は上記の手順 4 と 5 と同じである。
- バックエンドとの関係: 並び替えはバックエンドで行う。バックエンドの `UserResource.getAllUsers()` は `Pageable` を受け取り、並び順の列名が `id`、`login`、`firstName`、`lastName`、`email`、`activated`、`langKey`、`createdBy`、`createdDate`、`lastModifiedBy`、`lastModifiedDate` のいずれかであることを確認する。それ以外の列名なら 400 を返す（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/UserResource.java` の `ALLOWED_ORDERED_PROPERTIES` と `onlyContainsAllowedProperties()`）。この画面が送る 6 列はすべて許可された列名である。
- 状態変化: `sortState` または `page`、URL のクエリパラメーター、5.2.1 と同じシグナル群。
- 遷移: 画面遷移はない（同じルート `/user-management` のクエリパラメーターだけが変わる）。

#### 5.2.4 Activated、Deactivated ボタンクリック（有効・無効の切り替え）

- トリガー: `(click)="setActive(userManagement, false)"` または `(click)="setActive(userManagement, true)"`。
- 処理手順:
  1. `setActive()` は `this.userManagementService.update({ ...userManagement, activated: isActivated })` を呼ぶ。行のユーザーのデータの `activated` だけを変えたものを送る。
  2. `UserManagementService.update()` は `PUT api/admin/users/{login}` を送る。本文の日付（`createdDate`、`lastModifiedDate`）は `convertValueFromClient()` で ISO 8601 の文字列にする（5.3 参照）。
  3. 成功したら `load()` で一覧を再取得する。
  4. バックエンドは成功時にヘッダー `x-jhipstersampleapplicationapp-alert`（`userManagement.updated`）を返すため、`notificationInterceptor` が成功アラートを追加し、この画面の `<jhi-alert />` に「A user is updated with identifier {{ param }}」が表示される。
- 状態変化: 5.2.2 と同じシグナル群。
- 遷移: なし。
- 無効化の注意: ログイン中のユーザー自身の行では、Activated ボタンと Delete ボタンが `[disabled]` になる（`[disabled]="!currentAccount() || currentAccount()?.login === userManagement.login"`）。`Deactivated` ボタン（有効にする方向）にはこの制限がない。

#### 5.2.5 Delete ボタンクリック（削除ダイアログを開く）

- トリガー: `(click)="delete(userManagement)"`。
- 処理手順:
  1. `this.modalService.open(UserManagementDeleteDialog, { size: 'lg', backdrop: 'static' })` で削除ダイアログを開く。
  2. `modalRef.componentInstance.userManagement = userManagement` で、削除対象をダイアログに渡す。
  3. `modalRef.closed` を購読する。理由が `ITEM_DELETED_EVENT`（`'deleted'`）のときだけ `load()` を呼び、一覧を再取得する。
- 状態変化: ダイアログが開く。削除が確定した場合は、5.2.2 と同じシグナル群が変わる。
- 遷移: なし。ダイアログの中の処理（`DELETE api/admin/users/{login}`）は [ユーザ管理削除_画面設計書](../削除/ユーザ管理削除_画面設計書.md) に書く。

#### 5.2.6 リンクによる遷移

- トリガー: Create a new user ボタン、Login リンク、View、Edit、Profiles のバッジのクリック。
- 処理手順: `[routerLink]` に従って遷移する。遷移先のルートにも `canActivate: [userRouteAccessService]` と `data.authorities` がある。
- 遷移先: `/user-management/new`、`/user-management/:login/view`、`/user-management/:login/edit`、`/authority/:name/view`。
- 状態変化: この画面は破棄される。破棄のとき `<jhi-alert />`（`Alert`）の `ngOnDestroy()` が `alertService.clear()` を呼ぶ。

### 5.3 API呼び出し一覧

| No. | 目的 | メソッド | パス | 要求パラメーター | 応答 | 成功時 | エラー時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 一覧の取得 | GET | `api/admin/users` | クエリパラメーター: `page`（0 から始まるページ番号）、`size`（`20`）、`sort`（`<列>,<asc または desc>`。未指定ならなし） | 200: `IUserManagement` の配列。レスポンスヘッダー `X-Total-Count`（総件数）と `Link` | `userManagementsResource` が値を持ち、サービスの `userManagements` を経て画面の `userManagements` に入る。`totalItems` に総件数が入る | サービスの `userManagements` は空配列になる。エラーは `<jhi-alert-error />` に表示される |
| 2 | 有効・無効の切り替え | PUT | `api/admin/users/{login}` | 本文: 行のユーザーの `IUserManagement`（`activated` を変えたもの） | 200: 更新後の `AdminUserDTO`。ヘッダー `x-jhipstersampleapplicationapp-alert`（`userManagement.updated`） | 一覧を再取得する。成功アラートが出る | `<jhi-alert-error />` に表示される |

補足:

- 呼び出し元は `UserManagementsService.userManagementsResource`（`src/app/entities/admin/user-management/service/user-management.service.ts`）である。URL は `resourceUrl`（`${serverApiUrl}api/admin/users`）で、`serverApiUrl` はビルド時定数 `SERVER_API_URL` である（`src/app/config/endpoint.constants.ts`）。
- `UserManagementService.query(req?)` も同じ URL を `HttpClient` の `get` で呼ぶが、この画面は使わない。本体で `query()` を呼んでいる箇所はない。
- `IUserManagement` の日付の変換: サービスは応答の `createdDate` と `lastModifiedDate` の文字列を `dayjs()` で dayjs のオブジェクトにする（`convertValueFromServer()`）。送るときはその逆で、`toJSON()` で ISO 8601 の文字列にする（`convertValueFromClient()`）。
- 要求ヘッダーは `authInterceptor` が `Authorization: Bearer <トークン>` を付ける（トークンがあるとき）。バックエンドは `/api/admin/**` に `ROLE_ADMIN` を要求する（バックエンドの `src/main/java/io/github/jhipster/sample/config/SecurityConfiguration.java`、`UserResource.java` の `@PreAuthorize`）。
- バックエンドの `getAllUsers()` は `Page<AdminUserDTO>` の内容を本文に、ページ情報を `PaginationUtil.generatePaginationHttpHeaders()` でヘッダーに入れて返す（バックエンドの `src/main/java/io/github/jhipster/sample/web/rest/UserResource.java`）。`PaginationUtil` は JHipster フレームワークのライブラリーのクラスである。
- エラー時の共通の動きは次のとおりである。
  - 401 のときは `authExpiredInterceptor` が現在の URL を保存し、ログアウトして `/login` へ遷移する。
  - HTTP エラーは `errorHandlerInterceptor` がイベント `jhipsterSampleApplicationApp.httpError` として配信し、`AlertError` がステータスに応じた文言を `<jhi-alert-error />` に表示する（404 は `error.url.not.found`、到達できないときは `error.server.not.reachable`）。403 は本文に `message` がなければ本文がそのまま表示される。
