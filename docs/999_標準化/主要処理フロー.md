## 2. 認証

### 2.1 セッション復元（ページを開いたとき）

1. `Main.ngOnInit()` が `AccountService.identity()` を呼ぶ。
2. キャッシュ（`accountCache$`）がないため `AccountService.fetch()` が `GET api/account` を送る。
3. `authInterceptor` がストレージ上のトークンを `Authorization: Bearer {token}` として付ける。
4. 成功なら `authenticate(account)` で `account` シグナルに設定する。失敗なら `catchError(() => of(null))` により `null` を流し、未ログインとして扱う。
5. 同じころ `Navbar.ngOnInit()` が `ProfileService.getProfileInfo()` で `GET management/info` を呼び、結果から次を導く（`src/app/layouts/profiles/profile.service.ts`）。`inProduction`（`activeProfiles` が `prod` を含む）、`openAPIEnabled`（`api-docs` を含む）、`ribbonEnv`（`display-ribbon-on-profiles` と `activeProfiles` の一致）。`shareReplay()` により取得は 1 回である。

### 2.2 ログイン

```
Login.login()                                      src/app/login/login.ts
  └ LoginService.login(credentials)                src/app/login/login.service.ts
      ├ AuthServerProvider.login(credentials)      src/app/core/auth/auth-jwt.service.ts
      │   POST api/authenticate { username, password, rememberMe }
      │   レスポンス { id_token } を受け、authenticateSuccess()
      │     └ StateStorageService.storeAuthenticationToken(id_token, rememberMe)
      └ mergeMap(() => AccountService.identity(true))       force = true で必ず再取得
          └ GET api/account
             └ tap: authenticate(account)
                     → account.langKey があれば、保存された言語が無ければそれへ切替
                     → navigateToStoredUrl()
Login の next: authenticationError を false にし、ナビゲーション中でなければ router.navigate([''])
Login の error: authenticationError を true にする（テンプレートの data-cy="loginError"）
```

- `Login.ngOnInit()` は、既にログイン済みならホームへ遷移する。
- `loginForm` の 3 項目（`username`、`password`、`rememberMe`）はすべて `Validators.required` である。
- `rememberMe` が true ならトークンは `localStorage`、false なら `sessionStorage` に置かれる。ブラウザーを閉じてもログインを維持するかどうかの違いになる。

### 2.3 ログアウト

```
Navbar.logout()                         src/app/layouts/navbar/navbar.ts
  ├ LoginService.logout()               src/app/login/login.service.ts
  │   └ AuthServerProvider.logout()     トークンを localStorage と sessionStorage から削除
  │       complete → AccountService.authenticate(null)    キャッシュも消える
  └ router.navigate([''])
```

ログアウトでバックエンドを呼ぶことはない。

### 2.4 利用中にトークンが無効になったとき（HTTP 401）

```
api/account 以外の API が 401 を返す
  └ authExpiredInterceptor                src/app/core/interceptor/auth-expired.interceptor.ts
      ├ StateStorageService.storeUrl(router.routerState.snapshot.url)
      ├ LoginService.logout()
      └ router.navigate(['/login'])
再ログイン後、AccountService.identity() の navigateToStoredUrl() が保存した URL へ遷移する
```

### 2.5 ルートガード（ログインと権限）

```
canActivate: [userRouteAccessService]     src/app/core/auth/user-route-access.service.ts
  └ AccountService.identity()
      ├ アカウント有り
      │   ├ data.authorities が無い、または hasAnyAuthority(authorities) が true → 通過
      │   └ 権限が足りない → isDevMode() のとき console.error、/accessdenied へ遷移、拒否
      └ アカウント無し
          └ StateStorageService.storeUrl(state.url)、/login へ遷移、拒否
```

## 3. HTTP リクエストの共通処理（インターセプターの連鎖）

```
画面 / サービス の http.get / post / put / patch / delete
  │
  ▼ リクエストは配列の順に通る
  ① authInterceptor             Authorization: Bearer を付ける
  ② authExpiredInterceptor      （リクエスト側は何もしない）
  ③ errorHandlerInterceptor     （リクエスト側は何もしない）
  ④ notificationInterceptor     （リクエスト側は何もしない）
  │
  ▼ バックエンド
  │
  ▼ レスポンスは逆順に戻る
  ④ notificationInterceptor     成功レスポンスのヘッダーから成功アラート（§4.1）
  ③ errorHandlerInterceptor     エラーをイベント jhipsterSampleApplicationApp.httpError として配信（§4.2）
  ② authExpiredInterceptor      401 ならログアウトして /login へ（§2.4）
  ① authInterceptor             （レスポンス側は何もしない）
  │
  ▼ 呼び出し元の Observable
```

- 登録箇所は `src/app/app.config.ts` の `provideHttpClient(withInterceptors([authInterceptor, authExpiredInterceptor, errorHandlerInterceptor, notificationInterceptor]))` である。
- 画面がエラーを受け取るより先に、共通のログアウト処理とエラー表示が働く。そのため画面側の `error` コールバックは最小限でよい。

## 4. 通知

### 4.1 成功通知

```
バックエンドがヘッダーを付けてレスポンスを返す
  x-jhipstersampleapplicationapp-alert: <翻訳キー>
  x-jhipstersampleapplicationapp-params: <埋め込み値>
  └ notificationInterceptor                       src/app/core/interceptor/notification.interceptor.ts
      └ getMessageFromHeaders(headers)            src/app/shared/jhipster/headers.ts
          └ alertKey があれば AlertService.addAlert({ type: 'success', translationKey: alertKey, translationParams: { param } })
              └ AlertService 内部のシグナルに追加

```

- `alertMessage`（翻訳キーではないヘッダー値）の場合は、それを原文のまま表示する。
- 画面は `<jhi-alert />` を置くだけでよい。保存成功時の文言を画面で組み立てていない。

### 4.2 エラー通知

```
HTTP エラー
  └ errorHandlerInterceptor                       src/app/core/interceptor/error-handler.interceptor.ts
```

ステータスと表示内容の対応は `共通部品利用ガイド.md` §4.1 のとおりである。`AlertError` は自分のシグナルにアラートを溜めるため、表示は `<jhi-alert-error />` を置いた画面単位に閉じる。

## 5. ルーティング

- **定義の木**: `src/app/app.routes.ts`（最上位）→ 各機能の `*.routes.ts` / `*.route.ts`。遅延読み込みは `loadComponent`（画面 1 つ）と `loadChildren`（ルート群）を使う。
- **データの受け渡し**: `withComponentInputBinding()` により、`resolve` の結果とパスパラメーター・クエリパラメーターを画面の `input` で受けられる。詳細画面は `readonly bankAccount = input<IBankAccount | null>(null);` で受け、プロパティ名が `resolve` のキー名 `bankAccount` と一致している。
- **タイトル**: 遷移のたびに `AppPageTitleStrategy.updateTitle()` がルートの `title`（翻訳キー）を翻訳して `Title.setTitle()` で設定する（`src/app/app-page-title-strategy.ts`）。多言語切り替え時は `Main` が明示的に呼び直す。
- **ナビゲーションエラー**: `withNavigationErrorHandler` が `NavigationError` を受け、`e.error.status` に応じて `/accessdenied`（403）、`/404`（404）、`/login`（401）、`/error`（その他）へ遷移させる。
- **未定義のパス**: `src/app/layouts/error/error.route.ts` の `{ path: '**', redirectTo: '/404' }` が受け、`Error` 画面を表示する。`/accessdenied` と `/404` は同じ `Error` コンポーネントに `data.errorMessage`（翻訳キー）を渡す。

## 6. 国際化

### 6.1 翻訳データの読み込み

```
provideTranslation()                                   src/app/shared/language/translation.provider.ts
  ├ provideTranslateService({ loader: translatePartialLoader, missingTranslationHandler })
  └ provideAppInitializer:
      ├ translateService.setFallbackLang('en')
      └ translateService.use(StateStorageService.getLocale() ?? 'en')

translatePartialLoader().getTranslation(lang)          src/app/config/translation.config.ts
  └ from(loadLocale(lang))                             src/i18n/index.ts
      └ import('i18n/en.json')
          ビルド時に build-plugins/i18n-esbuild.ts が解決する
          （src/i18n/en/*.json を deepmerge で 1 つのオブジェクトに結合）
```

- `i18n/<lang>.json` は実在するファイルではない。esbuild プラグインが仮想モジュールとして解決し、言語ディレクトリ内の全 JSON をマージした結果を返す（`build-plugins/i18n-esbuild.ts` の `prepareLanguage`）。
- 単体テストでは `vitest-base.config.ts` のプラグイン `jhipster:i18n` が同じ解決を担う。
- トップレベルのキーはファイル間で重複してよい。`global.json` と `error.json` はどちらも `error` を持ち、マージされて 1 つの名前空間になる。
- 未定義のキーは `translation-not-found[<キー>]` と表示される（`MissingTranslationHandlerImpl`、`src/app/config/translation.config.ts`）。

### 6.2 翻訳キーの構造

| 接頭 | 内容 | ファイル |
|---|---|---|
| `global.*` | 共通文言（メニュー、フォーム、項目名、ボタン）。同じファイルに `entity.*`（アクション、検証メッセージ）、`error.*`、`footer` もある | `src/i18n/en/global.json` |
| `<画面名>.*`（`home`、`login`、`register`、`settings`、`password`、`activate`、`reset`、`configuration`、`health`、`logs`、`metrics`） | 画面固有の文言 | 同名の `<画面名>.json` |
| `jhipsterSampleApplicationApp.<entity>.*` | エンティティ固有の文言（`home.title`、`home.createLabel`、`<項目名>`、`delete.question`、`created` / `updated` / `deleted`） | `src/i18n/en/<entity>.json`（`bankAccount`、`label`、`operation`、`adminAuthority`） |
| `userManagement.*` | ユーザー管理の文言 | `src/i18n/en/user-management.json` |
| `sessions.*` | セッション管理画面の文言 | `src/i18n/en/sessions.json`（対応する画面は現状ない） |

### 6.3 言語の切り替え

```
Navbar.changeLanguage(languageKey)              src/app/layouts/navbar/navbar.ts
  ├ StateStorageService.storeLocale(languageKey)     sessionStorage に保存
  └ translateService.use(languageKey)
      └ onLangChange を Main が受ける            src/app/layouts/main/main.ts
          ├ titleStrategy.updateTitle(現在の routerState)     ブラウザータイトルを更新
          ├ dayjs.locale(lang)                                日付の書式・ロケールを更新
          └ renderer.setAttribute(<html>, 'lang', lang)
```

- `jhiTranslate` ディレクティブと各パイプは `onLangChange` / `onTranslationChange` を購読し、言語が変わると自動で再描画される。
- ログイン直後は、`account.langKey` があり、かつセッションに言語の保存が無ければ `account.langKey` に切り替わる（`src/app/core/auth/account.service.ts` の `identity()`）。
- 現在は `LANGUAGES` が `'en'` のみであるため、navbar の言語メニューは表示されない。

## 7. エンティティの一覧

### 7.1 共通の流れ

5 つの一覧画面（`BankAccount`、`Label`、`Operation`、`UserManagement`、`Authority`）は同じ骨組みである。

```
constructor 内の effect                               例: src/app/entities/bank-account/list/bank-account.ts
  (a) activatedRouteState（queryParamMap と data を toSignal 化）が変化
        └ fillComponentAttributeFromRoute(params, data)   sort / page をシグナルへ反映
        └ load() → queryBackend() → service.bankAccountsParams.set({…})
  (b) service.bankAccountsResource.headers() が変化      （Operation と UserManagement のみ）
        └ fillComponentAttributesFromResponseHeader(headers)
  (c) service.bankAccounts() が変化
        └ fillComponentAttributesFromResponseBody(data) → 画面の bankAccounts シグナルへ

service.bankAccountsParams が変化
  └ httpResource が再取得（params が undefined ならリクエストしない）
      └ bankAccountsResource → bankAccounts（computed）→ (c)
```

- (a) の effect は `untracked()` で包み、ルートの変化だけをトリガーにしている（コメント「Only watch for route changes.」）。
- 画面の `bankAccounts` は `refineData()` を通すことで、`sortState` に従ってクライアント側でも並び替える（全件取得の 3 画面のみ）。

### 7.2 3 つの形

| | 全件取得 | 無限スクロール | ページング |
|---|---|---|---|
| 画面 | `BankAccount`、`Label`、`Authority` | `Operation` | `UserManagement` |
| クエリ | `sort`（`BankAccount` は `eagerload: true` も） | `size`、`eagerload: true`、初回のみ `sort` | `page`（0 始まり）、`size`、`sort` |
| 続きの取得 | なし | `<tbody infinite-scroll (scrolled)="loadNextPage()">` で `links().next` のパラメーターを引き継いで再取得 | `<ngb-pagination (pageChange)="navigateToPage($event)">` で `page` を変えて再取得 |
| 必要なレスポンスヘッダー | なし | `link`（`headers.get('link')` を `ParseLinks.parseAll` で解析） | `X-Total-Count`（`TOTAL_COUNT_RESPONSE_HEADER`） |
| 結果の持ち方 | 取得ごとに置き換え | 既存の一覧にない ID だけ追記 | 取得ごとに置き換え |
| 件数表示 | なし | なし | `<jhi-item-count [params]="{ page, totalItems, itemsPerPage }">` |

`Operation` の続きページの判定（`src/app/entities/operation/list/operation.ts`）:

```ts
readonly hasMorePage = computed(() => !!this.links().next);
readonly isFirstFetch = computed(() => Object.keys(this.links()).length === 0);
// queryBackend(): size と eagerload を必ず渡し、
//   hasMorePage() なら links().next の内容を、そうでなければ初回だけ sort を加える
```

`UserManagement` のページ番号は URL のクエリパラメーター `page`（`PAGE_HEADER`）に持つ。画面では 1 始まりで扱い、リクエスト時だけ `page - 1` にする。

## 8. エンティティの詳細・登録・編集・削除

### 8.1 詳細画面

```
/bank-account/:id/view
  └ ルートの resolve: { bankAccount: BankAccountResolve }       src/app/entities/bank-account/bank-account.routes.ts
      └ bankAccountResolve(route)                               src/app/entities/bank-account/route/bank-account-routing-resolve.service.ts
```

### 8.2 登録・編集画面

```
/bank-account/new または /bank-account/:id/edit
  └ resolve: 同じ bankAccountResolve（new なら of(null)）
  └ BankAccountUpdate.ngOnInit()                                src/app/entities/bank-account/update/bank-account-update.ts
      └ activatedRoute.data を購読
          ├ bankAccount があれば updateForm(bankAccount)
          │     └ bankAccountFormService.resetForm(editForm, bankAccount)
          │     └ 関連の現在値を xxxSharedCollection に補う（add…ToCollectionIfMissing）
          └ loadRelationshipsOptions()
                └ UserService.query() → GET api/users → usersSharedCollection へ

save()
  └ bankAccountFormService.getBankAccount(editForm)             フォーム値をモデルへ
      ├ id === null → bankAccountService.create(bankAccount)    POST api/bank-accounts
      └ id !== null → bankAccountService.update(bankAccount)    PUT api/bank-accounts/{id}
          └ subscribeToSaveResponse
              ├ next → onSaveSuccess() → previousState()        1 つ前へ戻る
              └ finalize → isSaving を false に戻す
```

- 保存ボタンは `[disabled]="editForm.invalid || isSaving()"` で制御する。
- 保存の失敗は `onSaveError()` では何もしない。表示は §4.2 の流れで `<jhi-alert-error />` に出る。
- 関連を選ぶ `<select>` は `[compareWith]="compareUser"` を付け、選択肢の同一性を `compareUser(o1, o2)` で判定する。

### 8.3 削除

```
一覧画面の delete(bankAccount)                                  src/app/entities/bank-account/list/bank-account.ts
  └ modalService.open(BankAccountDeleteDialog, { size: 'lg', backdrop: 'static' })
      └ modalRef.componentInstance.bankAccount = bankAccount
削除ダイアログの confirmDelete(id)                              src/app/entities/bank-account/delete/bank-account-delete-dialog.ts
```

## 9. 並び替えの状態管理

```
<th jhiSortBy="name"> のクリック
  └ SortByDirective.onClick() → SortDirective.sort('name')     src/app/shared/sort/
      └ 同じ項目なら asc ⇄ desc、別の項目なら asc で sortState を更新し、sortChange を emit
          └ 画面 navigateToWithComponentValues($event) → handleNavigation(sortState)
              └ router.navigate(['./'], { relativeTo: activatedRoute, queryParams: { sort: buildSortParam(sortState) } })
                  └ クエリパラメーター sort が変わり、§7.1 (a) の effect が働く
                      └ sortState = sortService.parseSortParam(params.get(SORT) ?? data[DEFAULT_SORT_DATA])
                      └ load()
```

- 並び替えの状態は URL のクエリパラメーター `sort`（例: `?sort=name,asc`）に反映される。画面を再読み込みしても同じ並び順になる。
- `buildSortParam` は `'名前,asc'` の形の配列を返す。`parseSortParam` はその逆を行う。
- クエリパラメーターがないときは、ルートに `data.defaultSort` があればその値（`bank-account`、`label`、`operation` は `id,asc`）を使う。
